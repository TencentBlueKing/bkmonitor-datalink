alarmd 对象与判定

这个页面看的是按策略把时序数据判成异常或恢复、并把结果发出去这一段。 发出去之后的收敛、通知、送达不在这里——这一段正常，不等于告警已经送到人手上。
“对象”是什么，为什么对象数和策略数对不上

一个对象是一次查询：alarmd 把查询内容完全相同的策略合并成一次查询来执行， 所以多条策略可能共用一个对象，一条策略也可能因为有多个查询而落在多个对象上。 这就是为什么页面上“54 个对象”会关联到“70 条策略”——两个数不该相等。 下面的表按对象列，因为执行是按对象发生的；要找人处理得看“关联策略”那一列， 顶部的“业务影响”已经把同一批对象换算成了策略数和业务数。 对象标识是那次查询的指纹，本身不可读，也无法在监控 SaaS 上按它查到东西。

    判定规则、降级池为什么不计入、未知怎么来

    判定规则：证据不全 → UNKNOWN； 证据齐全且「没跑成待查」里有归到 alarmd 的 → DEGRADED； 副本级运行状态超出设计界，或策略缓存里有策略却一条都没被接受、且因此没有任何对象在检测（SOURCE_BLOCKED：不是没负载，是全被扣在配置获取环节）→ DEGRADED；缓存一条都不能用但对象仍按已生效配置在跑，只在“应有”格说明缓存不能用于更新，不降级； 证据齐全且一个都没有 → HEALTHY。
    判定看的不是整栏：「没跑成待查」是待处理清单，里面既有 alarmd 自己的，也有数据源没答、 策略配置写不了的。只有归到 alarmd 的那部分进判定——整栏进判定的话，别人家的故障面越大 alarmd 看着越差， 而这个数一直不为零的信号等于没有信号。
    降级池不参与判定：后端持续查不到的对象不计入判定。代价是这是个把对象移出分母的机制， 所以池必须有出口，“出过降级池”那一栏就是用来看出口的。只进不出有两种可能：出池路径坏了， 或者后端确实一直没恢复——这两种在池子大小上看起来一样。要分清看“冷却到期未重试”： 那是冷却已经到期、本该再查一次却没查的对象，它不为零才指向出池路径本身。
    未知怎么来：未知 = 应有 − 已知状态。它同时包含“没有副本认领”和“认领了但还说不出结论”两种。 只要未知不为零，判定就停在 UNKNOWN——不知道不等于健康。

    怎么读这张表（为什么带占比、哪一列不能横向比）

    部署总数回答“这个部署好不好”，回答不了“是不是某一个副本在扛”。 两个副本持有的对象数往往不一样，所以计数后面都带了占比——裸计数会把持有量的差异算进“谁更差”里。 “其中 alarmd 的”这一列要按“有没有副本大于 0”看，不要拿两个副本互相比： 对象归谁每次再平衡都会变，劈分会在什么都没发生的情况下移动。

    趋势

    卡片上的数是最后一个采样点，不是当前值；最低/最高是所选窗口内的，不是历史极值。

    这些曲线和上面的判定不是同一种读

    曲线读的是 alarmd 自己的指标，表达式写死在服务端，和判定用的是同一批数字。 但判定是此刻直读控制面，曲线是经采集、降采样的历史，最右端总比判定旧一个采集周期以上， 两者对不上一点是正常的。

    观察窗口

    对某一个对象记录接下来每一轮的详细过程，用来回答“这一轮到底发生了什么”。 适合已经定位到具体对象、但从上面的表里看不出原因的情况；上面的表已经说清楚的，不需要开窗。

    能看到什么、有什么限制

    看到的是每一轮各阶段的耗时与结果、查询发出与返回了什么、判定为什么是这个结论。 开窗只改变“记录什么”，不改变“执行什么”——不会影响检测结果，也不会改任何配置。 开窗那一刻起就在记录，不必等到期，点“查看记录”即可看到已经产生的内容。 窗口按自身到期时刻失效，最长 – 分钟；同时最多 – 个对象。 它消耗共享诊断预算并自动过期；装不下时会被截断并按次上报，不会静默生效。
