## 根因与现场证据

- 16:38:09–17:38:09，ProcessEvent 平均总耗时约 1.79 s；plan 执行 1373.79 ms，其中 suppression 1260.51 ms。
- 17:24:57–17:39:57，suppression 平均 1634.68 ms；17:39:57 的最近 60 秒平均 3.289 s、P99 9.881 s。
- `linkd-测试抑制` 的空间 `bkcc__524` 在当前租户 metadata_space 中为全局业务。租户有 323 个 cw-biz，完整分页返回约 0.9 MB 业务文档。
- EvaluateConditions 原先每次先 ResolveScope：全局空间分页读取所有业务，再查事件业务、目标身份和条件。缺少 canonical 实例字段的事件仍承担这项成本；同一目标解析还会再次展开全局空间。
- 每来源策略资源装配仅 4 个 HTTP 连接；消息突发时重复分页、JSON 解码/编码与连接等待叠加。现场 suppression 的 not_matched 累计求值均值约 3.15 s，说明正常未命中也在消耗时间。

- 同期抽样 ES CPU 2%–4%，写队列/拒绝为 0；基础 Event/Alert 存储多为几十毫秒。普通 processing_failed 丢弃按当前语义保留，不将业务报错本身作为根因。

## 修复边界

逐事件业务归属改为 ResolveBusinessScope，只查询本次业务 ID；真实全局标记、租户和业务存在性仍从当前权威源读取。缺少目标字段/模型不匹配先返回未命中。完整 selector 集合解析仍保持原有完整性与业务范围语义；不增加跨 Event 成员缓存，不修改消息失败丢弃规则。

## 移除逐事件策略快照和执行计划

按本次确认的处理语义，Linkd 不保证重投读取同一策略版本，也不保证补齐失败事件的全部输出。
取消 `processing.policy_context` 与 `processing.plan` 的持久化和恢复；策略读取、告警变更与流水构造只在当前调用内存在。
正常 Event 结果提交由策略快照、执行计划、最终结果三次 CAS 减为最终结果一次 CAS；Event Enrich 的来源丰富写入保留。
最终 `policy_decision` 保留实际裁决及其策略引用用于诊断，稳定 Alert 身份、租户隔离、原有 CAS 和 Mailbox 失败出队语义保持。

故障注入覆盖创建、更新、关闭、流水、最终结果、Recent Alert 缓存六个步骤：

- 12 个场景分别在写入前失败、真实写入后中断/响应丢失；重建 Processor，重投后再验证同 fingerprint 的后续触发、恢复、重新触发和关闭。
- 6 个场景将普通失败记录为 rejected/processing_failed，直接处理后续触发和关闭，不依靠重投失败事件修复。
- 换处理器时保留共享旧缓存，并推进处理时钟，避免测试仅因进程内计划或相同时间偶然成功。
- 另测历史 JSON 中包含退役字段时自然忽略，不新增迁移逻辑；策略读取回归确认失败后新尝试读取新版本，已终态重投不再执行。

必要调整仅包括：告警真实写入后立即更新 Recent Alert 缓存；创建失败但可能已经提交时，失败路径按已有稳定 ID 回读；同一源事件已生效时沿用真实告警，避免重复推进或覆盖后续控制命令。
没有增加新的补偿存储、校验链或重试协议。测试不承诺任意多依赖同时故障下完整补齐输出；本次底线是后续合法事件能够继续推进业务状态，不被旧计划、版本或身份冲突永久卡住。
