# 筛选关闭批量化与字段收敛验证

日期：2026-10-29，2026-10-30 更新。初始源码基线：`4098fd4b4d23e77e1f9b34846aeaa5f24f5cefd7`。
前三轮测试部署暴露了重复读取、逐项 Redis 请求及 ES 字段过滤开销，不能视为吞吐验收通过。
最终测试镜像基于 `ade2ccdfaca6d814ebd69e8fd782f85b7de86725`，已验证 5000 条预算续调及两请求并发关闭 8000 条；
单批放大与更高并发仍存在超时边界，不能据此宣布 6.5 万条整轮性能验收通过。接口说明见
[主动关闭 API](../reference/contracts/alert-close.md)，配置见[配置指南](../guides/configuration.md)。

## 问题与证据边界

调用方报告原 `close_filter` 逐条执行，单条约 0.4–1.5 秒；控制面在请求轮次结束时出现 lease 获取
和同步投影超时。调用方提供的 `stage=projection` 平均值约 84ms。本次没有重新读取该环境日志或指标，
这些数值仅作为问题输入，不能据此认定投影是唯一瓶颈，也不能直接线性推导策略关闭墙钟时间。

源码确认原候选读取、关闭入口及同步投影均携带完整 Alert；筛选关闭串行共享十秒截止，
终态清理还会通过 `configuredCleanupRecorder` 为每条打开策略存储并检查 schema。
现已参考 `merge-batches` 的显式阶段组织关闭：身份批读、fingerprint 租约、锁内批读、Bulk CAS、
pipeline 缓存、输出与流水批写、租约释放、同步投影。来源配置、连接、Hook 和清理 Journal 复用控制面资源。

## 字段与批次

- 候选查询只返回 `alert_id`；普通完整告警检索仍保持 500 条分页上限。
- 租约准备只读租户、Alert ID、来源、来源版本和 fingerprint 五个字段。
- 关闭裁决只读身份、状态、屏蔽/合并意图及清理、无数据联动必需原始事实，不读取正文、标题或 Enrich。
- Alert CAS 只替换 12 个状态及派生字段，保留每项 `seq_no/primary_term`。对象按顶层整体替换，防止递归
  合并遗留旧屏蔽 bindings 或合并 pending。未变的业务正文和丰富数据不再回写。
- 关闭终态只作为 active lookup 的负缓存；状态缓存不携带正文、丰富与扩展数据。来源恢复缓存仍保持完整快照。
- KAC 已有文档只更新 `status/action/source_alarm_status/close_reason/close_time` 五个字段，不强制 refresh；
  不存在时才为缺失项读取完整快照创建。
- 按本次确认移除通用 Kafka V1 Hook，遗留声明及多余参数忽略，不装配客户端、执行 Hook 或生成 push 流水。
  当前 KAC 插件使用轻量变更通知；仅仍显式启用的旧 `type: kac` Kafka Hook 需要完整输入快照。

筛选关闭使用独立配置 `control_plane.close`：默认 `batch_size=1000`、`concurrency=8`、
`member_concurrency=32`。请求最多 5000 个候选，ES 和流水继续遵守各自既有字节/数量预算。
这些名额不与单条关闭、查询或 Lifecycle Worker 共用。筛选关闭仍为同步且每请求二十秒，批次按预估耗时检查剩余预算；已启动批次超时仍可能部分生效。

## 原型实测后的修正

首次原型的 1000 条批次未在十秒内完成。阶段指标定位到重复活动文档读取，以及关闭后逐项更新
依赖索引、清理和通知。锁内读一度约 6.01 秒；先读写目标、仅对缺失项回退其他位置后，
降为约 3.25 秒，但索引/缓存阶段仍约 4.19 秒，不能靠成员并发视为已完成批量化。

当前进一步改为：租约获取/释放、依赖候选、活跃分组、近期缓存、依赖主清理、复查提示、
计数/聚合主清理及轻量通知全部按阶段 pipeline。Journal 使用批量 `_mget` 和 Bulk 保存两个阶段，
从 Bulk 响应取得后续版本；来源处理器只构造一次。同步关闭投影复用本次成功关闭返回的不可变终态快照，免去重复读取，通知在同步投影尝试结束后统一入队。流水支持 5000 条逻辑批次并按请求字节切块。
5000 条的单元/协议用例检查实际 pipeline/Bulk 次数，并覆盖取消、部分失败和原身份重试。
真实环境结果见下文，不能将本地调用次数等同于生产吞吐。

## 真实环境阶段诊断

前三轮均未满足十秒同步预算，不能据此宣称吞吐验收通过。第三轮已把常规内部路径改成
pipeline/Bulk；1000 条的租约获取约 157ms、释放约 21ms，索引约 497ms、近期缓存约 130ms，
但身份读取约 817ms、锁内读取约 3.17 秒、清理约 2.29 秒、流水约 1.58 秒，导致同步投影开始时预算耗尽。

随后对同一组 1000 条、每条正文 4 KiB 的测试告警执行只读对照：

| `_mget` 返回方式 | 墙钟 | 响应体积 |
| --- | ---: | ---: |
| `_source_includes` 选择关闭所需字段 | 3.02 秒 | 1,183,548 字节 |
| 完整 `_source` | 0.59 秒 | 5,469,548 字节 |
| 只排除正文、标题、丰富字段 | 0.74 秒 | 1,291,548 字节 |
| `filter_path` 在响应编码时选择相同字段及版本元数据 | 0.55 秒 | 1,155,548 字节 |

据此把窄字段裁剪移到响应编码阶段，避免逐文档重复构造 source 过滤器。仍使用实时 `_mget`，
不返回正文、标题、Enrich 或其他 ExtraData，也不改变 CAS 版本及后续裁决。上述读对照只是
定位依据，最终端到端耗时需以下一次测试部署为准。

## 同步投影改异步的评估

当前普通变更通知入队失败只记录日志，不阻止业务关闭；普通投影失败后也会确认当前消息，
没有补偿扫描。因此直接去掉同步等待或忽略投影错误，可能返回成功却永久留下旧 KAC 状态。
本次保留“同步写入成功才返回成功、失败 502 且原命令可补齐”的现有契约，把逐项投影改成窄字段批量写入。
异步关闭需要先明确成功究竟代表 Linkd 关闭还是 KAC 投影完成，并选择可恢复的投影失败处理方式；
这属于后续契约与恢复设计，本次没有增加后台任务、第二份水位或确认记录。

最终测试配置恢复 `batch_size=1000`，关闭请求并发设为已实测的 `concurrency=2`，
`member_concurrency=32`；代码默认请求容量仍为 8。请求同步预算仍为二十秒。
失败轮次的原生关闭可能已经保存，需按原操作身份补齐，不能只重搜 active 候选当作全部完成。

失败测试按原操作通过同一批量关闭服务补齐输出后，全量只读核对结果为：原生告警 65002 条，
全部 closed、active 为 0；KAC 对应终态 65002 条，原生关闭流水 65002 条。
这是多轮测试及失败补齐后的最终数据核对，不是一次关闭 65002 条的性能数据。
专用测试来源已停用，未删除测试告警或其流水。最终生产代码提交的完整 `make check` 通过；

2000 条批次中，身份读约 0.83 秒、锁内读 1.63 秒、CAS 2.00 秒、索引 2.92 秒、缓存 1.76 秒、

说明这轮超时不能再归因于全局投影通道锁。去掉强制 refresh 后，KAC 定位和 Bulk 写入仍需实际 I/O 时间。

测试环境外部 Helm 发布曾覆盖直接更新的 Deployment；最终镜像与关闭配置仍需纳入后续环境发布值，
避免下次 Helm 发布恢复旧配置。本次未整体升级其他组件。

当前结果证明了批处理和预算续调行为，尚未覆盖 6.5 万条一次连续压测、生产负载、真实 Hook、
无数据外部回调及多副本故障恢复；不能将不同版本和失败后补齐的测试告警累计数视为单次吞吐结果。

## 并发投影与脚本正文

4 并发、每批 1000 条的真实试验发现，大批次几乎占满固定投影通道，导致无关批次也被串行化。
现改为仅对同租户同 Alert ID 的读写串行，重叠批次按身份排序取锁；普通队列仍保留原分区顺序。
关闭投影直接使用本次成功关闭返回的不可变终态快照，缺失 KAC 文档才实时补读完整快照。

Redis 依赖候选、终态清理和租约释放的 pipeline，改为首条 EVAL、后续 EVALSHA；同一连接的命令顺序
保证脚本先载入缓存，避免每个成员重复发送脚本正文，不新增业务身份或校验规则。5000 条清理协议用例
验证每种脚本只发送一次正文，成员的独立结果及未知清理语义保持原样。

## 投影成功语义调整

按本次确认，主动关闭的 KAC Bulk（包括缺失文档创建）使用 `refresh=false`，写入被接受即返回，
不再强制搜索刷新。正常索引刷新后 KAC 查询才可见，后台动作执行前原有刷新仍保留。
批量顶层仍为 HTTP 200，逐项结果不确定仍使用 `502/result_uncertain`，保持原命令重试；
已关闭项不会被解释成未执行，也不会因其他成员失败而回滚。


## 请求内自动取数和并发修正

上述 `close-batches.8` 只实现批量 I/O，内部块仍串行；两 HTTP 请求并发不能替代单请求批次池。
随后提交 `173ef5674` 仍保留了全局并发和调用方数量控制，已按确认要求进一步删除，不作为最终发布版。

最终接口只接收关闭条件和原操作信息，不再接收数量或游标。服务每块自动读取 1000 个候选 ID，
单请求默认并发 8，在二十秒预算内按空闲名额继续取数。已完成块的平均墙钟用于新块准入，剩余时间不足
停止启动，最终汇总实际结果及 `has_more`。不再以 5000 条作为整轮处理上限。

只保留 `control_plane.close.concurrency` 一个并发配置，用于每个请求自己的批次池。
删除关闭路径的全局请求/批次限制和 `batch_size`、`member_concurrency` 配置，不占用普通检索槽。
每个块内部的来源/成员操作顺序执行，避免再叠加一层并发；批读、Bulk/pipeline、清理、流水及投影仍按块提交。
不新增持久关闭任务、摘要或确认记录，原操作身份、逐项结果及 `refresh=false` 保持。

回归验证覆盖单请求自动处理 20000 条（20 个物理块，默认并发 8）、两个请求的并发名额相互独立、
普通检索槽占满时关闭仍能工作、取消和部分成功、后续查询错误保留已有结果，以及预算不足不读取下一块。
真实环境 2 万条测试数据另行记录，不用这些内存/协议测试替代部署吞吐。
