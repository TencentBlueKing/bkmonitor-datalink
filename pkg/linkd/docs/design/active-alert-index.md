# 活跃告警缓存与软限流

状态：2026-10-26 主流程增量维护，控制面差异修复。配置格式与运维步骤以
[使用指南](../guides/active-alert-by-strategy.md)为权威位置。

## 职责

持久化 Alert 是事实来源。EventSource 的 `active_alert_limits` 声明字段分组、近似阈值、集合命名和可选通知，
全部使用内部 `storage.redis`。已移除独立的 `active-alert-by-strategy` Hook、输出 Redis 和完整快照发布。
活跃集合同时服务软限流和外部 fingerprint 查询，不维护另一套策略计数。

控制面在来源发布前为已有、启用且缺少策略规则的 `built_in_bk` 补默认 5000。默认配置包含公开集合与通知，
通过 Record/Release 保存；已有策略规则及显式关闭不覆盖。普通运行时只执行配置，不识别来源名称。
未来 KAC 下发相同规则后可删除默认补齐代码，不改变缓存引擎。

## 主流程

Cleaner 标准化后先幂等写 Event，再批量检查缓存。未满组只查数量，默认短暂缓存一秒；满额才查活跃 fingerprint。
新 fingerprint 被限流时保存带诊断的 suppressed 终态，不入 Mailbox/Enrich。恢复、关闭和已有活跃身份继续通过。
Lifecycle 在创建/终结时尽力增量更新集合；持续触发不写，升级轮换接替原成员。成员真实变化才通知。

每条规则仅维护按租户和字段分组的 Redis Set，成员只有 fingerprint。
数量直接用 SCARD；满额时对相应组执行 SMISMEMBER。没有独立计数、成员 Hash、租户目录、就绪标记或扫描临时集合。
主流程的 Lua 只合并成员增删与通知，不实现额度预占；已有生命周期幂等和 fingerprint lease 负责主流程串行化。
缓存读失败时 Cleaner 放行，写失败只在边界记录并由后台修复。Redis 丢失时空集合按零处理，允许重建期间超量。

## 差异修复

控制面先分页读取数据库 active，仅投影身份和规则原始字段；MySQL 单条 SELECT 流式交付，ES 使用 PIT。
按页批量查 Set 成员关系，缺失项才进入已有 fingerprint lease 并实时读取 Alert 后补齐。
然后 SCAN 当前规则前缀下的 Set，SSCAN 分批读取 fingerprint，以租户、来源和一批 fingerprint 查询活跃原始字段。
只有终态残留或归组不符的成员进入同一 fingerprint lease，按当前活动状态增删；健康成员不逐条回源、不重复写缓存。
ES 复用既有 Recent Alert 缓存跨越 refresh 窗口。扫描失败停止本轮，不把错误解释为空结果。

修复不以旧快照整体覆盖在线集合，不保存 Seen 或来源租约；多个控制面可重复核对，实际差异修复由既有 fingerprint 锁串行化。
扫描中新增但未出现在查询结果的成员也要在锁内读取当前状态，不直接删除。
任务有来源操作期限和单页预算，失败后下一轮继续。清空规则或修改前缀后不再维护原集合，旧前缀按需人工清理。

## 边界

限额允许因采样、并发、在途事件和故障放行而突破，没有固定超量保证。
实时活动成员不设 TTL；Pub/Sub 只表示集合需要重读，订阅者仍需周期补读。
默认策略集合仅属于 built_in_bk；自定义前缀必须由一个部署、来源规则独占。
上线需要停止旧写入者、发布新配置并对齐 alarmd 的内部 Redis 连接；本地检查不代替目标环境接入验收。
