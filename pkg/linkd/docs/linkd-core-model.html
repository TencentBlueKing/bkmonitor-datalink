01 / OVERVIEW

一条主线，四种数据职责

上游 MQ 负责确认前重投，Redis Mailbox 负责确认后的生命周期待办；Repository 中各对象通过稳定身份和单对象 CAS 收敛，而不是依赖跨对象事务。

Input RawEventMessage

稳定 record ID、租户、来源、received_at、headers 与原始 payload。

→
Cleaner output Event + EventProcessing

Event 保存来源事实；Processing 独立记录生命周期裁决结果。

→
Lifecycle output Alert + AlertLog

Alert 是当前态，AlertLog 是状态操作与最终输出的不可变流水。

!

最重要的分界：Event 不是 Alert，Event 的 action 不是 Alert 的 status，EventProcessing 的 state 也不是 Enrich 的执行状态。它们解决的是不同问题，不能互相代替。

03 / CLEANER

Cleaner：先落事实，再确认来源

Cleaner 不查询或修改 Alert，不做生命周期裁决。它只把一条来源消息确定性地变成 Event， 并在 Event 持久化和 Mailbox 入队之后确认原消息。

SourceCleaner 负责什么

  • 确定性解释某种来源 payload，输出 EventDraft。
  • 当前只注册 standard；输入必须是单个 JSON object。
  • 展开嵌套 subject、来源 event/alert ID、来源 severity 等已知字段。
  • 重复 key、尾随 JSON、非法 action 或已知字段非法值确定性拒绝。
  • 不得访问 Repository、Mailbox、MQ Session 或产生外部副作用。

EventFactory 独占什么

  • 租户覆盖、EventSource、标准 severity 和接收时间。
  • 确定性 Event ID；来源 Event ID 为空时使用稳定 record ID。
  • 按 EventSource 配置从展开字段计算 fingerprint。
  • 保存完整 source_raw_data，未知字段只在该快照中保留。
  • 时间稳定回退、动态对象深拷贝、UTC 规范化和领域终检。
ID

fingerprint 不是消息输入字段。它由 EventSource 配置从已展开的稳定 Event 字段计算；source_event_id 是单条来源事件身份，source_alert_id 是来源告警实例身份，source_raw_data 是追溯快照，三者不能混为一谈。

共享 worker pool

消息到达后立即进入共享 worker pool。纯清洗不按 fingerprint 或 OrderKey 串行，worker 可以乱序返回 Event、Discard 或暂时错误。

每个 lane 单独推进

每个 lane 只取队首连续完成前缀，按消息数、字节或等待时间成批执行副作用。一个慢 lane 不应阻塞其他 lane，但后续消息不能越过本 lane 的缺口。

确认条件与故障恢复

位置 / 结果 能否确认 恢复方式
确定性无效输入 → Discard 可以，且必须仍处于 lane 连续前缀 无需业务重试
Event 已存储 + Mailbox 已入队 可以，且必须连续 后续由 Redis Mailbox / Lifecycle 接管
Event 存储失败 不可以 MQ 重投；稳定 Event ID 保证幂等
Event 成功、Mailbox 失败 不可以 MQ 重投；Event create 收敛为已存在
Mailbox 成功、Confirm 失败 不可以视作完成 允许重复引用，由 Event 终态短路收敛
Retry / timeout / lost ownership 不可以越过缺口 保留未确认 Receipt，由当前或新 owner 重投
04 / LIFECYCLE

Lifecycle：按关联键串行裁决

Lifecycle 只处理已持久化且为 unprocessed 的 Event。它通过 Redis Signal 唤醒 Mailbox，在分布式 lease 保护下逐个处理队首事件。

Signal 只负责“唤醒这个 Mailbox”，真正待处理的 Event ID 存在 Redis List 中；空到非空时写入 Signal，允许重复 Event 引用和冗余空唤醒。lease 使用 compare-token 的续租与释放，旧 owner 不能误删新 owner 的锁。

“最后统一落盘”的准确含义：同一次裁决产生的 AlertLog 统一批量提交， 并把 EventProcessing CAS 放在全部日志项成功之后。Alert create/CAS 仍先发生， Alert、AlertLog 与 Event 之间仍没有跨对象事务。

Event active Alert EventProcessing Alert 结果
triggered 不存在 accepted 创建 active Alert，执行 Enricher

典型分支的副作用顺序

创建 stable Alert ID → Enrich → CreateAlert(wait_for) → FinalHook → [trigger + push] Bulk(refresh=false) → Event CAS accepted(refresh=false)
同等级推进 Alert CAS(wait_for) → FinalHook → [push] Bulk(refresh=false) → Event CAS accepted(refresh=false)
来源终结 Alert CAS terminal(wait_for) → FinalHook → [recover/close + push] Bulk(refresh=false) → Event CAS accepted(refresh=false)
等级抑制 [suppress] Bulk(refresh=false) → Event CAS suppressed(refresh=false)
等级升级 close old(wait_for) → create new(wait_for) → old/new FinalHook → [close + push + trigger + push] Bulk(refresh=false) → Event CAS accepted(refresh=false)
直接关闭 Alert CAS closed(wait_for) → FinalHook → [close + push] Bulk(refresh=false)
✓

AppendAlertLogs 按输入顺序返回逐项结果。只有请求成功、结果数量一致且每一项 都没有错误，Processor 才继续写 Event 终态；Bulk 部分成功时保持 Event 为 unprocessed，由重试通过稳定 log_id 吸收已成功项。

Processor 如何收敛部分成功

ANCHOR 01Event 已终态

日志批次已经全部成功，直接返回保存的 Processing 结果。

ANCHOR 02latest_event_id 命中

说明 Alert CAS 已完成，补齐输出与 Event 终局即可。

ANCHOR 03trigger_event_id 命中

说明 Alert 已由该 opening Event 创建，继续幂等收尾。

ANCHOR 04FindAlertEndedByEvent

识别来源终结或等级升级已完成的旧 Alert。

ANCHOR 05确定性 ID

Bulk 部分成功或 FinalHook 重复时，AlertLog 与 Kafka message ID 仍可收敛。

ANCHOR 06有界 CAS 重试

最多 3 次；冲突后重读并重新裁决，不用旧 replacement 覆盖。

Enricher

只在创建新 Alert 前同步执行。error、panic、非法状态或非法 JSON 降级为 failed + {}，不阻断 Alert 创建；当前 Noop 实现返回空的 succeeded。

FinalHook

在 Alert 真实变化后输出当前快照，但不立即写日志。成功或失败结果先转换为 push AlertLog，再与本次状态日志统一 Bulk；日志全部成功后才写 Event 终态。

ES

Elasticsearch 的 Alert create/CAS 使用 refresh=wait_for，保证同 fingerprint 的后续 Event 能看到最新 Alert。AlertLog Bulk 和最终 Event CAS 使用 refresh=false，成功后仍可能在一个 refresh interval 内无法被 search 看见； 当前没有运行中的 Event Replayer，未来扫描必须避开这段可见性窗口。

05 / DEPLOYMENT

两种部署模式，一套运行职责

两种模式共享同一套领域逻辑、存储结构和消息协议，只改变 Cleaner、Lifecycle 与控制面如何装配和扩缩容。外部 Kafka、Redis、MySQL 或 Elasticsearch 不包含在进程内。

TEST / SMALL SCALE

All-in-one

linkd run all-in-one
CleanerLifecycleControl Plane

一个进程复用正式实现，适合本地测试、集成验证和小规模部署。共享 CPU、内存、连接预算、 telemetry endpoint 与故障域；任一内部任务异常会取消其他任务并整体退出。

SCALE / ISOLATION

三进程模式

linkd run cleaner · lifecycle · control-plane
独立扩缩容独立发布故障隔离

Cleaner、Lifecycle 和 Control Plane 成为三种逻辑进程角色，副本数与资源预算分别设置。 主数据流仍通过 MQ、Repository 和 Redis Mailbox 协作，不增加同步 RPC 捷径。

三进程职责与 Metrics

ROLE 01

Cleaner

linkd run cleaner

消费 Raw Event MQ，构造并持久化 Event，写入 Lifecycle Mailbox 后确认上游消息。

/metrics · linkd.role=cleaner
ROLE 02

Lifecycle

linkd run lifecycle

消费 Mailbox Signal，按 fingerprint lease 串行裁决 Alert，落 AlertLog 并执行 FinalHook。

/metrics · linkd.role=lifecycle
ROLE 03

Control Plane

linkd run control-plane

统一装配低吞吐、需要单一所有权的管理任务；每个任务不是独立进程，也没有顶级 command。

elasticsearch-storage-manager
redis-stream-manager

M

Metrics 不是单独进程。每个常驻进程都会创建 telemetry runtime；拆分模式下 Cleaner、Lifecycle 和 Control Plane 分别暴露 /metrics。部署在独立 Pod 时可使用 相同端口，共享宿主网络时必须配置不同的 listen_address。

Command 类型 行为

CP

当前控制面已经实现 Elasticsearch 索引/归档管理任务与 Redis Stream 观测/安全裁剪任务； API 和 Leader Election 仍是规划。Leader 完成前，拆分模式的 Control Plane 只能部署单副本。 All-in-one 仅在配置了至少一个管理任务时启动控制面职责。

06 / BOUNDARIES

当前实现边界

下面把“仓库里已经存在的能力”和“部署或架构仍需承担的责任”分开列出，避免把设计目标写成已完成事实。

IMPLEMENTED

当前代码已有

  • Event / Processing / Alert / AlertLog 领域约束
  • standard Cleaner 与 EventFactory
  • Kafka Cleaner Flow、Redis Mailbox 与 Signal
  • Lifecycle 状态矩阵、Enricher、FinalHook
  • 同次裁决 AlertLog 批量追加，最后 CAS Event 结果
  • 内存 / MySQL / Elasticsearch Repository
  • All-in-one 与 Cleaner / Lifecycle / Control Plane 进程入口
  • Elasticsearch 与 Redis Stream 控制面管理任务
  • 单元、race 与可显式启用的外部 E2E 入口
SAFETY BOUNDARY

必须由部署保证

  • Event、Alert、AlertLog、Kafka 之间没有跨对象事务
  • AlertLog Bulk 返回逐项结果，不承诺整批事务
  • 上游确认后，Lifecycle 待办依赖 Redis 持久化与复制
  • Redis Mailbox 整体丢失不能从已提交 Kafka offset 精确恢复
  • ES refresh=false 写入存在短暂的 search 不可见窗口
  • Leader Election 完成前，Control Plane 只能部署单副本
  • 生产并发、批次、超时与容量预算必须基于真实载荷压测
  • 外部服务 E2E 未显式运行时不能表述为已验证
NOT IMPLIED

本页不代表

  • 旧 Kingeye / KAC 行为自动成为 Linkd 契约
  • 历史嵌套 KingeyeAlertEvent 仍是目标模型
  • 文档中的候选模块名已经定稿
  • 存在通用跨对象事务或 durable inbox
  • 直接关闭已有公开 HTTP / CLI / Kafka 入口
  • API、Leader Election、自动 retention 或分桶迁移已经落地
