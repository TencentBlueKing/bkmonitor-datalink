# Lifecycle 与 Elasticsearch 吞吐压测

测试日期：2026-09-04～2026-09-06。

## 1. 主要结论

- **本轮建议配置已完成两次目标 1000 Events/s、十分钟验证。** 使用三进程、Lifecycle 并发
  256，自动派生写批次 128 项/128ms、读等待 10ms、共享执行上限 32；ES 单节点 4 CPU /
  4 GiB、heap 1 GiB、两主分片零副本，Redis 1 CPU / 1 GiB。第二轮沿用相同进程和已有索引。
  两轮末两分钟处理速率分别为 997.8/s、999.5/s，未出现持续未读积压，停止输入后全部排空；
  十分钟均值约 981/s，包含生成器爬坡，不能写成十分钟平均精确 1000/s。详见 4.25～4.26。
- **本次剩余性能限制主要在客户端的批次/并发配合与依赖等待放大，而不是已经证明 ES 写盘饱和。**
  在 Redis 恢复后，相比 512 并发配置，256 及其派生批次使末段写批次约 26.5ms 降至约 7.2ms、
  逐项响应解析约 7.3ms 降至约 1ms、调度 P99 约 64ms 降至约 10ms；分配量仍约 620 MiB/s。
  这不是“并发越大越快”，也不能把 GC 分配量当作唯一原因。现有数据支持上述组合调整有效，
  不据此宣称某个 Go 调度器缺陷已被唯一定位。
- **拆分进程没有消除降速，后续调参又被 Redis OOM 干扰。** 三进程十分钟 Lifecycle 均速
  832.3/s，后程仍慢；因此不能把共用 Go 堆视为唯一原因。随后仅将 Lifecycle 执行并行度
  从 14 降到 4 的试验中，Redis 触及 512 MiB 上限、RDB 失败并最终退出，该轮不作为容量或
  参数优劣结论。随后保留数据恢复 Redis 并补齐持久化与内存指标，再完成后续对照。详见 4.22～4.23。
- **同批两端计时表明，当前四倍执行耗时增长主要不在 ES Bulk 的 took 区间内。**
  新诊断基线中客户端执行从 9.32ms 升至 37.55ms，同批 ES took 仅从 4.33ms 升至 6.62ms；
  客户端逐项解析和 Go runnable 调度延迟明显增长，连接/执行槽位等待很小。
  非 Active 刷新从 5s 延长至 10s 未恢复吞吐。去掉客户端重复规范化和写编码后，
  完整十分钟复测的 Lifecycle 均速由 757.2/s 提高到 873.7/s，末两分钟由 655.6/s 提高到
  849.0/s；但调度尾延迟仍高、后程仍有积压，尚未达到持续 1000/s。详见 4.19～4.20。
- **读侧短窗口合批显著减少请求，但仍未消除后程降速。** 本地单节点 4 核 / 4 GiB、
  独立 ext4 数据卷上，增加最多 10ms 的读收集窗口后，平均读批量由 1.76 增至 39.35，
  物理读请求由约 903/s 降至 43/s；Lifecycle 十分钟均速由 707.7/s 增至 755.0/s，
  但最后两分钟仍只有 674.3/s。写批次执行时间在本轮从约 9.5ms 增至 37.9ms，
  请求响应等待和客户端响应处理均有增长，不能把局部合批收益描述为持续 1000/s 达标。
- **远端 ES 对照未复现本地的持续降速，但仍未达到 1000/s。** 两节点、每节点 2 核 / 8 GB、
  heap 4 GiB 的远端 ES 上，Lifecycle 十分钟均速为 534.7/s，前后段分别约 547.5/553.9/s。
  写批次平均 207.2 个操作、执行 142.6ms，读取平均 53.2ms；远端请求延迟明显更高。
  ES 每节点平均消耗约 1.4 CPU 核，没有写入拒绝。随后将 Lifecycle 并发从 512 提高至 1024，
  十分钟均速升至 616.6/s（约 +15.3%），但写批次耗时从 142.6ms 增至 262.7ms，仍未达到目标。
  版本、网络、硬件和存量分片不同，不能将远端与本地比较解释为单一内存扩容实验。
- **后续对账定位到 Signal 串行逐条确认的限速机制。** 降速窗口 2,046 个在途 Signal 中，
  1,810 个已完成但等待确认，仅 236 个 Handler 正在执行；确认通道占用约 96%。
  已完成项占住在途名额，限制新任务接收，写侧凑批变慢是下游现象之一。
  已实现仅对 Redis 开启有界批量确认；运行收益与剩余限制仍以修复版验证为准。
- **后续定位到确定的 Cleaner 空转缺陷，不能再把客户端存储耗时直接归因为 ES 内部瓶颈。**
  执行中的批次仍触发过期组批定时器，重复扫描与指标上报；单消息、200ms 模拟存储的隔离对照中，
  快照次数由 356,234 降至 5。正式修复后的同积压短时回切未复现 Cleaner 吞吐回归；
  进一步批量核对 Event 重复项后，10 分钟 Lifecycle 平均约 722/s，仍未达到持续 1000/s。
- **测试 Kafka 还存在独立的内存配置问题。** 双节点初次验证中，1 GiB 容器发生 OOM kill；
  broker 之外额外启动的 Java 采样进程进一步挤压了内存。修正 Kafka 与采样后仍复现降速，
  因而该故障不是全部降速的解释，也不能忽略它对早期实验归因的干扰。

- **归档等待和 Stream 裁剪不足是早期的明确限制。** 移除归档的 refresh 等待、增加连续裁剪后，
  Stream 可围绕软上限收敛，但 Lifecycle 在持续输入下仍会降速。
- **增加 ES 内存没有单独解决降速。** 2 GiB 扩到 4 GiB 后，文件缓存压力减轻，Lifecycle 仍从约
  800/s 降到 360～450/s；不能把问题全部归因于内存不足。
- **真正的大批次改善了有效写入吞吐。** 调整合批调度、分离读写队列并匹配调用并发后，平均每批
  79.35 个写操作，3 分钟窗口完成 937.3 Events/s，Signal lag 为 0～1。
- **1000/s 收尾测试未达到持续承载目标。** 最终自动合批配置在 10 分钟测试中仍保持平均 78 个
  写操作/批，但第 4 分钟开始降速，后六分钟约 434～521/s；输入结束时 Kafka lag 约 19.4 万。
  合批已经生效，不等于整个持续处理瓶颈已经消除。
- **分区尾部慢是另一类问题。** Kafka 长 fetch 与分区暂停/恢复叠加，产生约 5 秒的拉取周期；
  定向对照将恢复后的等待从约 4.8 秒降到了毫秒级。

937.3/s 包含历史积压追赶，且只覆盖短窗口；后续 1000/s 长一些的窗口再次出现降速。
各轮环境和改造不同，
本报告不据此给出生产配额或“某规格 ES 必然支持多少 Events/s”的映射。
1000 Events/s 指本报告既定模型的输入投递速率，包含 20% 重投，不是每秒 1000 条独立新告警。

## 2. 测试条件与指标口径

### 2.1 环境与负载

| 项目 | 条件 |
| --- | --- |
| 运行形态 | 单节点 all-in-one；共享 macOS/arm64 宿主机，Apple Container 虚拟块设备 |
| Elasticsearch | 7.17.7；2 vCPU；容器内存 2 GiB 或 4 GiB，heap 按轮次注明；零副本 |
| Redis | 7.2.16；1 vCPU / 512 MiB；AOF 关闭 |
| Kafka | 3.9.1；2 vCPU / 1 GiB；两路输入，每路 3 个分区、单副本 |
| 输入分布 | infra/service 新告警数量约为 1:2 |
| 告警模型 | 周期 1 秒，平均存活 20 个周期，重复投递比例 20%，每个新告警使用独立 fingerprint |

稳态下，每个新告警约产生一次 triggered 和一次 resolved，因此本模型的换算为：

```text
Events/s ≈ 新告警数/分钟 × 2 × 1.2 ÷ 60
```

600 Events/s 对应两路合计约 15,000 个新告警/分钟，800 Events/s 对应约 20,000 个，
1000 Events/s 对应约 25,000 个。
该换算不适用于任意生产负载。

初始 Lifecycle 并发为 8。Cleaner 两路分别使用 4/8 个 worker、64/128 条批次和 1/2 个并行批次；
单分区在途上限为 256，恢复阈值为 128。后续轮次只在注明时改变相关参数。
R1～R5 使用 2 GiB ES 容器、512 MiB heap；R6 将 heap 调为 1 GiB，R7 起容器内存为 4 GiB。

### 2.2 如何解读结果

- 表中的吞吐是 Lifecycle 完成的 Events/s；目标输入速率、完成速率和 ES 文档操作数不是同一指标。
- Signal 是 Mailbox 的调度引用，两者积压不能相加当作未处理 Event 总量。
- ES translog 是已执行写入的恢复日志，不是待执行请求队列。
- 批次大小按 ES 文档操作计数，不按 Event 计数；一个 Event 可能依次产生多类写入。
- 早期部分 Lifecycle 延迟混用了 Handler 和 Processor 口径，本报告不使用这些值做跨轮比较。
  大批次结果中的 Event 延迟仅按 Processor accepted 计算，Bulk 耗时不包含入队等待。
- 持续输入时还需观察 Kafka/Signal 是否增长、归档是否追平、Stream 是否收敛及错误率。
  短窗口追平、停流后排空，均不等同于长期稳定。

## 4. 各项改进的效果与证据

### 4.1 取消归档 refresh 等待，增加 Stream 连续裁剪

**改进前：**

- History create 和 Active delete 使用 `refresh=wait_for`。归档批次平均约 4.92～4.95 秒，
  满批 1,000 条对应约 200 Alerts/s。
- 600 Events/s 负载约产生 250 个终态 Alert/s，超过上述归档速度。
- Stream 每 60 秒最多裁剪 10,000 条，理论上限约 166.7 entries/s；440/s 测试中，
  Signal 新增约 357 entries/s，长度仍会增长。

**改进：** 归档改为 `refresh=false`，冲突通过 realtime 读取核对；Stream 每轮在总预算内连续裁剪，
每批重新检查所有 Group/PEL 的安全边界，默认周期缩短为 10 秒。

| 指标 | 改进前 | R5 改进后 |
| --- | --- | --- |
| 归档 | 满批耗时接近固定 5 秒 | 不再受固定 refresh 等待限速；累计归档 128,802，无归档失败 |
| Stream 裁剪 | 每轮最多一次，追不上新增 | 累计新增 247,101、裁剪 150,000，长度 97,101 |
| Lifecycle | 600/s 后程降至约 508/s | 后程仍降至约 326/s |

**结论：** 改造解决了已识别的后台任务限制，但没有解决全部性能问题。
不能根据“归档等待已移除”推断 Lifecycle 必然稳定。

### 4.2 查询目标修正、归档平滑与内存对照

R6 将 Active lookup 限定到 Active alias，终态恢复查询使用 Active 与 History；
归档由 30 秒/4 worker 调为 5 秒/单 worker，并将相关索引 refresh 统一为 5 秒。
归档约 333～368 Alerts/s 时，terminal backlog 仍保持在调度窗口量级，未成为这一轮的持续积压源。

| 阶段 | R6：2 GiB 容器 / 1 GiB heap | R7：4 GiB 容器 / 1 GiB heap |
| --- | --- | --- |
| 前约 3 分钟 | Lifecycle 约 795～799/s | Lifecycle 约 794～799/s |
| 后程 | 曾降至 308.6/s，存在波动 | 多个窗口约 360～450/s |
| 文件缓存 | 典型样本约 0.62 GiB；10 秒内 842 次 file refault、28 次 major fault | 典型样本约 2.31 GiB；降速阶段 refault/major fault 未持续增长 |
| JVM | 未见 Old GC | 未见 Old GC |
| ES write rejected | 0 | 0 |

**结论：** 2 GiB 下存在文件缓存压力，但扩大容器内存后仍会降速，因此内存不足不是充分解释。
同期多类 ES 操作的延迟都上升，而 Lifecycle 只有有限数量的同步请求链，积压可以先出现在
Signal/Mailbox，不需要先填满 ES write queue。

R6 累计约 15.03 GiB block write、63.55 秒 merge、14.35 秒 merge throttle；
R7 分别约 12.03 GiB、48.04 秒、8.74 秒。这些数据说明存在更新、删除和后台合并成本，
但**累计写入量、平均带宽或累计 I/O time 不能单独证明 SSD 饱和，也不能证明 fsync 是唯一根因**。

### 4.3 AlertLog async 降低同步写成本，但没有消除拐点

R8 仅调整 AlertLog durability；Event、Active、History 仍使用 `request`。
与 R7 相近测试阶段相比：

| 阶段 | AlertLog request：Lifecycle | AlertLog async：Lifecycle |
| --- | ---: | ---: |
| 约第 4 分钟 | 484.5/s | 805.0/s |
| 约第 5 分钟 | 417.4/s | 659.5/s |
| 约第 6 分钟 | 392.8/s | 415.2/s |

async 组早期 AlertLog append 平均约 0.65～0.71ms，后程升至约 1.73ms。
30 秒高频采样中，ES write queue 最大 1、rejected 为 0，仍未出现持续的服务端写队列积压。

**结论：** 减少 AlertLog 同步点延后了降速，但剩余串行读取、CAS 和其他写入仍有限制。
这支持继续优化请求形态，而不是仅增加 heap 或扩大 ES write queue。

**代价：** async durability 下，异常故障可能丢失最近一个同步周期内已返回成功的 AlertLog，
不能把该配置当作无损的性能优化。

### 4.4 合批参数必须与实际就绪操作匹配

合批覆盖 Event result CAS、Alert CAS、Alert create、AlertLog create。
同一 Event 的依赖写入仍逐步等待结果，不能提前提交后续日志或终态。

初始参数扫描结果如下。C 为 Lifecycle 并发，P 为批次执行并发，W 为最大等待时间。

### 4.8 双节点诊断与 Cleaner 空转定位

两个 ES 数据节点分别承载每个索引的一个主分片。总 ES 资源由 2 CPU / 4 GiB 提升为
4 CPU / 8 GiB，总 heap 由 1 GiB 提升为 2 GiB；没有新增副本。R13 使用新建索引，
R14 保留故障前已落库并完成恢复的数据。因此节点数、总资源和初始数据均不同于单节点实验。

R13 的 Kafka 内核日志明确记录内存 cgroup OOM kill：1 GiB 容器内 broker 的匿名驻留内存
约 942 MiB，同期还有额外的 Java 管理进程。原采样方式会增加受测 broker 的内存压力；
不能将这次 broker 停止产生的吞吐下降记为 ES 性能劣化。
R14 重建 Kafka，容器内存改为 3 GiB，JVM 初始 heap 512 MiB、上限 1 GiB，并从宿主机使用
轻量客户端读取 offset。该轮没有发生 Kafka 内存越限或 OOM，仍出现持续降速。

R14 的对齐输入窗口为 600.21 秒，Lifecycle 写 Bulk 4,748 次、写操作 994,511 项，
平均 209.46 项/批；Bulk 执行均值 24.06ms、首项等待 137.30ms，末尾 Signal lag 9,568、
PEL 2,044，未出现 Repository failure、retry 或 ES write rejected。后半程包含线程采样和
隔离诊断测试，本轮用于故障定位，不作为与 R12 的纯容量对照。

**已确认的代码机制：** Cleaner 在发起批次后保留 lane 队首，直到批次完成并确认；
但 `nextWake` 仍使用该队首的过期组批期限，返回立即唤醒。主循环没有实际可推进的工作，
仍重复扫描所有 lane、创建运行快照并调用指标上报。槽位占满的待发批次也存在同类风险。

| 隔离条件：1 条消息，存储等待固定 200ms | 快照上报次数 | 消息完成 |
| --- | ---: | --- |
| 修复前实现 | 356,234 | 正常 |
| 临时诊断版本：排除执行中批次的组批期限 | 5 | 正常 |

现场 Linkd 线程采样同时出现 Cleaner 主循环、下一次唤醒计算、指标属性处理、大量对象分配和
GC 路径，支持该缺陷确实影响当前进程。Cleaner 与 Lifecycle 同处一个进程，会共享调度和 GC
成本；这提供了 ES 客户端调用耗时增长的另一条具体解释，而非 ES 内部写盘饱和的证明。

隔离对照只确认空转机制，不等于已证明全部降幅均由它造成。正式修复还需覆盖槽位耗尽、
槽位释放与完成通知顺序、重试和退出；需要修复后同配置复测，才能量化实际吞吐收益。
此阶段尚未修改正式 Cleaner 运行代码。

121.2ms；Alert 写入、AlertLog 写入和 Event CAS 的逻辑耗时同时增长。末段读取约 1,052 请求/s，
平均仅 1.25 项/批。按执行时间总量折算，读写平均执行中合计约 9.5 批，低于上限 32；
该平均值不能排除短时槽位耗尽。

两个 ES 节点在上述末段窗口各平均消耗约 0.74 CPU 核，未发生 Old GC；窗口末尾读写队列为零。
因此目前确认的是客户端请求链路与多步同步等待增长，尚不能归因为 ES 内部写盘或线程池饱和。
新增诊断将凑批、共享执行槽位、逐操作排队、HTTP 连接获取、首字节及响应解码分别计时，
并记录聚合触发原因；现有首项等待不能替代逐操作平均等待。

### 4.11 Signal 串行确认造成的在途名额占用

进一步对 R17 进行同窗口确认计数对账，定位到比凑批等待更靠前的明确限速点：
`SettlementIndividual` 将每个完成项单独排入确认队列，且全局只有一个确认请求在途。
消息即使已经完成业务处理，也要等确认成功后才释放 `MaxInflightMessages` 名额。

| R17 对齐窗口 | 前段 | 后段 |
| --- | ---: | ---: |
| 确认请求均值 | 1.01ms | 2.70ms |
| 确认 Signal 速率 | 948.2/s | 356.5/s |
| 确认通道执行占用 | 96.0% | 96.4% |
| 窗口末在途 Signal | 824 | 2,046 |
| 已完成、等待确认 | 561 | 1,810 |
| 正在执行 Handler | 263 | 236 |

已完成待确认数由累计 Handler complete 减去累计成功确认消息数得到；该窗口无确认失败、
Discard 或重试干扰。两列均满足“在途 = 已完成待确认 + 正在执行”，后段绝大部分在途名额
被已完成消息占用。它直接解释了有未读积压时处理并发仍未充分利用、后续写操作到达变慢的现象。
Signal 可以排空多个 Event，因此不能把确认 Signal/s 直接当作 Event/s。

修复仅对声明支持安全批量独立确认的 Redis Session 启用：同 lane 已完成项合并到未发送尾批，
上限复用现有拉取批量，不主动等待；已发送或失败待重试的批次保持不变，确认成功后再释放名额。
Kafka 累计前缀确认及其他未声明批量能力的适配器保持原行为。
单元/竞态测试和 Redis 集成已验证数量上限、lane 隔离、在途及重试批次不变、结果未知重试、
不连续 ID 确认和其他 Group Pending 保护。吞吐收益仍以修复版负载验证为准。
单次确认请求耗时为何增长仍未完全归因，不把串行调度限制等同于 Redis 服务端性能故障。

R18 保持 ES、Lifecycle 合批和 Cleaner 并发配置不变，启用 Signal 批量确认后完成 10 分钟验证。
Lifecycle 全窗口均速 721.2/s，Cleaner 723.6/s，仍未达到持续 1000/s；输入末尾 Kafka lag 153,940，
但 Signal lag 仅 2、PEL 249。后程每次确认约 4～5 条，已完成待确认从上千条降到零或几十条，
确认通道不再持续占满。说明修复消除了确认名额占用，但并没有解决系统整体降速。
最终 Cleaner 处理 587,896 条，Lifecycle accepted 587,636 条，另有 260 条终态重复项在入口收敛；
Kafka、Signal、Mailbox 和归档 backlog 排空，Stream 为 93,048 条。

没有按 EventSource 拆 Stream。真实 Redis 已验证隔离、容量/错误 key 的失败前缀和响应丢失重试；
ES/MySQL 双后端 E2E 均通过。

### 4.13 Go 等待快照与结论修正

同配置诊断负载中采集了 20 秒 CPU、阻塞和 goroutine 快照。采样跨越吞吐变化前沿，
不是独立的稳定容量窗口，也不能把含空闲 worker 的阻塞总时长当作 CPU 消耗。
结束快照中 512 个 Handler 有 485 个停在 ES 批处理器等待路径：191 个 realtime 读取、
236 个 AlertLog 写入、14 个 Alert create、23 个 Alert CAS、21 个 Event CAS；
等待 Redis 连接池的只有 1 个，不支持先扩大 Redis 连接池作为主要修复。

进一步检查执行 goroutine：两个已发送写批次承载 133、150 个调用，一个含 174 个调用的读批次
正在读取响应，其他小读批次也在执行。**不能把这些 Handler 的等待全部归为发送前凑批。**
多数调用需要等所属物理批次及响应分发完成；这是同步依赖和批次完成粒度带来的等待，
尚不能单凭该快照区分全部 HTTP、服务端及客户端调度成本。

CPU 样本中 `JSONObject.Normalize` 累计约占 16%，JSON 解析、分配与系统调用也有明显成本，
说明“业务判断少”不代表整个 Go 请求路径轻量。这是进一步减少重复 JSON 处理的依据，
但没有快慢阶段独立 CPU 对照，不能认定它单独导致了持续降速。

诊断输入停止后，Kafka、Signal、Mailbox 与归档积压均排空，恢复未启用 profiling 的普通版本。
本轮没有继续调整批次参数、Redis 连接池或 Stream 划分；持续 1000/s 的目标仍未完成。

这些指标不能直接与客户端请求首字节或 Bulk 完成时间相减归因。

### 4.22 三进程隔离对照

将控制面、Cleaner、Lifecycle 拆成三个独立进程，均使用响应复用版；ES、Redis、
各角色业务并发、批次参数及输入模型不变，Go 执行并行度均为 14。

### 4.28 pprof 定位与重复规范化优化

在另一组空索引上复现约第 4.5 分钟降速，并分别采集正常段、降速段的 CPU、allocs、block、
mutex 和 5 秒 execution trace。Lifecycle 两次 allocs 快照的差分累计约 148GB，其中
`JSONObject.Normalize` 调用链约 75.5GB（51%）；`GetEvent → decodeEventHit` 约 63GB，
Event 终态 CAS 约 45GB。Cleaner 差分累计约 88GB，其中 `JSONObject.Normalize` 调用链
约 59GB（67%）；Mapper 和 `CreateEvents` 在同一 Event 上重复进行动态 JSON 规范化。
ES WriteBatch 调用链只占 Lifecycle 差分分配约 8%，不是主要分配来源。

execution trace 的降速段显示，`WriteBatchTransport.finish` 向调用方 channel 发送结果后的
runnable 延迟显著增加；mutex 样本主要落在 runtime heap、GC 和调度内部，而不是业务互斥锁。
这组证据将“客户端 GC/调度竞争”定位为重复动态 JSON 解码和复制引起的结果，不再只根据
Prometheus 阶段耗时推断。诊断使用默认关闭、仅允许回环地址的 pprof endpoint；原始 profile
保留在本地诊断目录，不作为仓库制品提交。

据此保留外部输入和 ES 文档边界的完整校验，只移除同一可信调用链中的重复工作：

- ES Event 文档完成 Normalize 后，StoredEvent 只再检查 processing 与关联字段约束，不重新解析动态 JSON；
- Event 终态 CAS 对本次 realtime 读取并校验的 Event 只修改关联标量，不 Clone 后再次 Normalize；
- Cleaner Factory 已规范化 Event 后使用类型化批量创建快速路径，Repository 仍检查身份、路由、时间桶和载荷上限。

| Cleaner GC 暂停占比 | 5.41% | 2.09% |
| 写批请求体均值 | 140.7KiB | 85.3KiB |
| 写批执行 / ES took | 12.88 / 3.16ms | 8.66 / 3.30ms |

投影与局部更新使写批请求体下降约 39%，而 ES `took` 基本不变；Lifecycle 分配下降约 31%，
写批完成缩短约 33%。最终轮十分钟内 Kafka lag 和 Signal 未读始终为零，停止输入时 PEL 为零；
约 15 秒后终态归档积压归零。CPU、allocs 差分和 scheduler 图见

## 5. Kafka 单分区尾部慢的定向验证

### 5.1 现象与改进

吞吐测试末尾曾仅剩一个 partition 积压，Cleaner 约 51.2 条/秒，每分钟 pause/resume 各约 12 次。
单分区在途上限 256，`256 / 5s = 51.2/s` 与实测速率吻合；同期 ES 批写平均约 27ms，
Lifecycle 单 Event 平均约 12.6ms，不足以解释秒级拉取空档。

改进是将 Kafka `FetchMaxWait` 从客户端默认的 5 秒显式缩短为 100ms，
不改变分区在途上限、暂停/恢复滞回或连续 ACK。

### 5.2 对照数据

测试使用同 broker 的三个分区，仅向 partition 1 写入 1,024 条有序消息，停止生产后再消费。
每收到并确认 256 条，暂停该分区 200ms；暂停期间继续拉取其他空分区，再测量恢复后的等待。

| fetch 等待 | 三轮 1,024 条处理耗时 | 恢复到下一批到达 |
| --- | --- | --- |
| 5s | 15.038s / 15.041s / 15.033s | 九次均为 4.805～4.811s |
| 100ms | 0.647s / 0.655s / 0.651s | 九次为 7.52～16.34ms |

耗时从首批到达开始计算，包含三次固定的 200ms 暂停，不包含消费组首次分配时间。
三轮均保持消息顺序、完整性和连续确认；追加对照结果为 15.041s / 0.635s，与上述结果一致。

**结论：** 在该场景下，有积压分区暂停后，对其他空分区的长 fetch 会拖延恢复拉取。
缩短 fetch 等待消除了秒级空档。这与 ES 写入效率是两个独立问题，不能把 Session 耗时差
当作端到端吞吐提升比例。更短等待会增加空闲 fetch 请求量，仍需关注大量来源下的 broker 开销。

## 6. 结论边界与后续验证

本轮已分别验证归档/裁剪改进、大批次写入效果、Kafka 尾部等待机制，并曾通过 4.25～4.26
的合理配置完成两次目标 1000/s、十分钟验证，第二次保留同进程与已有索引；4.27 在更晚的累计
运行现场没有复现该容量，空索引只能改善、不能消除后程退化。尚未完成的验证包括：

- 更多重复样本、不同初始数据状态下的随机对照，以及更长时间持续负载。
- 不同 Lifecycle 并发、ES CPU/内存规格和实际业务事件比例下的容量曲线。
- 大批次的低流量延迟、故障恢复时间，以及缩短 fetch 等待后的空闲请求开销。

因此，早期 440/s 的有限窗口结果与后期 937.3/s 的短时追赶结果都不应直接转换成生产 SLA。
当前证据支持优先改善请求粒度、同步依赖和拉取调度，不支持仅凭 ES 写队列为空、累计写盘量或
单次内存快照认定全部瓶颈所在。
