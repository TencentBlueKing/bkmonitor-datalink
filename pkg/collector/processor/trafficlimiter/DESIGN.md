# bk-collector 服务级字节限流（traffic_limiter/gcra）实现方案

> 对应代码：`pkg/collector/processor/trafficlimiter/`。本文描述当前实现，参数均为代码中的常量。

## 1. 目标与约束

| 目标 | 说明 |
|---|---|
| 按 `{token, service}` 限制计费字节速率 | 计费字节 = 逻辑字节 × 信号权重（traces / metrics / logs），三种信号扣同一个服务的额度，服务之间互不挤占 |
| 多个 Collector 实例共享同一份额度 | 额度保存在 Redis，所有实例共同受约束 |
| 请求路径不依赖 Redis | 绝大多数请求只做内存判断；Redis 变慢或不可用不能拖住请求 |
| 限额之内不丢数据 | 负载均衡导致的流量转移、单实例突增，只要总量在额度之内就不能被拒 |
| 毛刺有上界，之后必须限住 | 允许有限的突发，持续超限时总量稳定在额度 |
| 持续超限时公平、不饿死 | 需求小的实例拿满需求，剩余额度在需求大的实例间平分 |
| 配置问题只降级、不中断 | Factory 永不返回错误，任何配置问题都不会让 Pipeline 建不起来 |

## 2. 总体结构

```
                        ┌──────────────── Redis（每个服务）────────────────┐
                        │  {key}:{sha}         共享 GCRA 桶（TAT，唯一真实额度）│
                        │  {key}:{sha}:demand  需求表 Hash：实例ID → 需求,时间 │
                        └───────────────▲──────────────────────────────┘
                                        │ 批量 Lua（租约 / 退还 / 上报需求）
                                        │ 同一时刻至多 1 个在途
   ┌───────────────────── 每个 Collector 实例 ──────────────────────────┐
   │                                                                   │
   │  请求 ──► limit() ──► 本地余额（分片锁，内存）──► 放行 / 拒绝         │
   │              │  余额不足且可等待：合并成 1 次紧急补货，≤50ms          │
   │              ▼                                                    │
   │        补货泵 goroutine（quotaSyncer）                              │
   │          · 定时同步 500ms±25%  · 异步补货（低水位，≥20ms 间隔）      │
   │          · 紧急补货（等待中的请求）· 需求下降扫描 100ms              │
   └───────────────────────────────────────────────────────────────────┘
```

- **共享桶是唯一真实额度**：速率 `L = bytes_per_second`，容量 `C = max(burst_bytes, L × 1s)`。
- **本地余额是预取下来的额度**：请求在本地扣减；余额由补货泵向共享桶领取（租约），用不完的退还。
- **需求表只用于额度紧张时的公平分配**，不参与正常放行。

## 3. 数据结构

### 3.1 Redis

| Key | 类型 | 内容 | 过期 |
|---|---|---|---|
| `{redis.key}:{sha256(token, service, L, B)}` | String | 共享 GCRA 的 TAT（微秒） | `PX = TAT − now`，额度完全恢复后自动删除 |
| 同上 + `:demand` | Hash | 字段为实例 ID，值为 `需求速率,上报时间,公平额度,额度时间`；另有 `__scarce` 字段记录紧张起始时间 | 每次写入后 `PEXPIRE 10s`；读取时剔除 2s 未上报的字段 |

- Key 对 Token 和服务名做摘要，Redis 中不暴露明文。
- 额度（L、B）参与摘要：配置变化自动换到新的满桶和新的需求表，旧 Key 靠过期回收。
- 实例 ID = 主机名 + 8 位随机数，进程启动时生成；同一进程内 Reload 前后共用。必须唯一，不需要跨重启稳定。

### 3.2 本地（每个 `{token, service}` 一个 `quotaBucket`，64 个分片锁）

| 字段 | 含义 |
|---|---|
| `balance` | 空闲的计费字节（已经兑现给等待者的不在其中）。共享模式下来自租约，可透支到 `-overdraft()`；本地模式下按速率补充 |
| `mode` | 共享 / 本地降级 / 本地独立（无 Redis） |
| `arrived`、`measuredAt` | 本周期到达的计费字节（放行 + 被拒，不含超过 burst 的） |
| `demand`、`avgCost` | 上一周期的到达速率；平滑后的单个请求大小 |
| `need`、`waiters` | 等待紧急补货、还没兑现的请求（按到达顺序）及其所需字节之和 |
| `limitedUntil` | 退避截止时间：之前不再等待、不再按需补货 |
| `queued` | 已提交异步补货、尚未返回 |
| `leased` | 进入共享模式以来是否领到过额度 |
| `share`、`peers` | Redis 返回的公平份额与存活实例数，降级时使用 |

闲置 30 分钟的服务状态与指标 Label 被机会式回收（扫描间隔 5 分钟，不启动常驻 goroutine）。

## 4. 请求路径

`Process()` → 未开启额度的 Token 直接短路（不计算字节、不碰 Redis）→ 计算每个服务的逻辑字节 → `limit()`。

### 4.1 判断模式

| 条件 | 模式 | decisions 指标 |
|---|---|---|
| 没有可用的 Redis 客户端（未配置或配置非法） | 本地独立：每实例按 L、C 限流，从满桶开始 | `local / no_client` |
| Redis 健康，且距最近一次同步成功 ≤ 1s | 共享 | `redis / none` |
| Redis 变慢（见 10.1），且距最近一次同步成功 ≤ 1s | 共享、不等待，余额不够时先欠着（见 10.2） | `redis / timeout` |
| 其余（租约出错、或超过 1s 没有同步成功） | 本地降级 | `local / 最近一次失败原因` |

### 4.2 第一遍（只读写内存）

对请求中的每个服务：

1. 不限流的服务直接放行。
2. `cost > burst_bytes`：**直接拒绝**（`exceeds_burst`），不计入需求、不领额度、不等待。
3. 计入需求（`arrived`、`avgCost`）。
4. `balance ≥ cost`：放行并扣减。共享模式下若扣后低于预取目标的 1/4、未在退避、未排队，提交一次**异步补货**（不等待）。
5. 余额不足：
   - 本地模式（独立或降级）：拒绝。
   - 共享模式、未在退避：加入**等待集合**。
   - 共享模式、在退避：在**透支上限**之内放行，否则拒绝。

### 4.3 第二遍（仅当等待集合非空）

1. 为各服务登记一个**等待者**（`need` 随之增加；登记时余额若已经够，当场兑现、不再等），
   把整个集合合并成**一次紧急补货**，最多等 `50ms`。一个请求无论涉及多少服务只等一次。
2. 任何一轮补货写回时，按到达顺序把授予直接扣给付得起的等待者（first-fit），称为**兑现**。
   兑现过的额度不再留在 `balance` 里，补货泵紧接着开始的下一轮、需求下降时的退还、后到的请求都拿不走它。
3. 等待者醒来：已兑现的直接放行；没兑现的撤下登记，在透支上限之内放行，否则拒绝。
4. 等待超时：标记 Redis 变慢（之后的请求不再等待），没兑现的等待者按欠账放行（见 10.2）——它们的需要已经在
   这一轮申请里，补货回来就把欠账还上。补货失败：没兑现的等待者按本地降级判断。

兑现必须发生在写回的同一把锁里。若授予先加进余额、等待者被唤醒后再自己扣，中间的空档会让下一轮把这笔授予
当成空闲余额少申请（`peers ≥ 2` 时甚至当成超过两倍目标的富余退回 Redis），后到的请求也会先把它扣走，
等待者只能吃透支。2026-10-20 的真实压测里「每秒倒满一桶」「切流后满桶倒给存量实例」的限额内 429 都来自这里；
仿真在一个 goroutine 里逐个判断，每个等待者独占一轮补货，看不到这种交错。

### 4.4 什么时候会等 Redis

**只有**「共享模式 + 余额不够 + 不在退避 + 请求不超过 burst」才等，实际只出现在：

- 某服务在本实例上冷启动的第一个请求；
- 突增快于预取，余额在异步补货返回前耗尽。

每次至多 50ms，通常为一次 Redis RTT。稳态流量、超限流量（透支或直接拒绝）、Redis 变慢或故障期间的请求都只做内存判断。

被拒的请求一律不扣余额、不产生欠账。

## 5. 补货泵（`quotaSyncer`）

每个 Redis 客户端一个 goroutine，**同一时刻至多一个 Redis 调用在途**，调用期间到达的申请自动并入下一轮。

| 触发源 | 时机 | 间隔约束 |
|---|---|---|
| 定时同步 | 每 500ms，每次 ±25% 随机（让各实例的先后顺序每轮不同） | — |
| 异步补货 | 余额低于预取目标的 1/4 | 两次之间 ≥ 20ms |
| 紧急补货 | 请求等待（4.3） | 不受间隔约束 |
| 需求下降扫描 | 每 100ms 扫描内存，余额超过预取目标两倍的服务 | 只在发现时访问 Redis |

### 5.1 一轮租约做什么（`prepare` → Lua → `apply`）

对每个涉及的服务：

- **定时同步**额外结算需求：`demand = 本周期到达字节 / 周期时长`（不衰减），清零 `arrived`。
- 预取目标 `target = min(需求估计 × 0.75s, C / (2 × 存活实例数))`；还没拿到存活实例数（冷启动）时为 0，只领真实需要。
- 先兑现余额够付的等待者；之后 `balance` 只是空闲余额，`need` 只是还没兑现的等待者。
- 申请量 `want = max(need, target) − balance`（余额为负时自动包含欠账），不超过 C。
- 必须满足的部分 `required = min(need + 欠账, want)`：等待中请求的真实需要与透支欠账，这些字节已经到达或已经放行。
- 余额超过 `2 × target` 时退还多余部分（`want < 0`）。
- 上报需求估计（字节/秒，不超过 L）。
- Redis 不健康时 `want = 0`：只上报需求，同时作为恢复探测；没有任何服务时发一个空批次探测。
- Redis 健康且没有需要申请的服务时**不访问 Redis**（平台给所有 Collector 下发 Redis 而额度为 0 时，空闲实例没有任何 Redis 调用）。

服务多于 256 个时分批提交。某一批失败时撤销尚未成功的部分（退还的余额加回）。

### 5.2 写回结果（`apply`）

- 授予量加到余额；`leased` 置位。
- 授予量小于申请量时进入**退避**（见 8）：额度真正紧张、或连 `required` 都没领到时退避等待；只是预取没领满时只暂停异步预取。
- 按到达顺序把授予兑现给等待者（见 4.3），`need` 随之减少；更新 `share`、`peers`。
- 申请之后服务被回收或额度已变化：丢弃这笔授予（新额度对应 Redis 中的新桶）。

## 6. Lua 脚本（每个服务）

输入：实例 ID、同步周期、需求失联时长、预取窗口；每服务 `L、C、want、demand、required`。

```
now = TIME（微秒，统一各实例时间源）
读需求表：剔除 2s 未上报的字段，取出本实例的公平额度与 __scarce（紧张起始时间）
demands = 存活实例的需求 + 本实例需求(≤L)，D = Σ，n = 实例数
D ≤ L：share = demand + (L − D)/n
D > L：share = maxmin(demands, L)[本实例]               # 水位法
credit = min(share × 2T, 上次额度 + share × 距上次额度时间)  # 公平额度，只有正向授予才扣减

avail = (now + C/L − TAT) × L
pressed = D > L 且 avail < C/2；pressed 开始时记下 __scarce，解除时删除

want < 0：TAT 回拨，不早于 now                            # 退还
D ≤ L：grant = min(want, avail)                            # 不紧张
pressed 不到一个周期，或 avail ≥ C/2：                      # 突发、过时需求：先到先得
    grant = min(required + min(want − required, max(0, avail − required − C/2)), avail)
pressed 持续一个周期以上：                                  # 持续超限：公平
    grant = min(want, avail, max(credit, avail − (L − share) × 0.75s))，scarce = 1
credit −= grant；TAT += grant/L
返回 {grant, n, share, scarce}
```

关键在于第二种情况：突发会让瞬时需求虚高、刚退出的实例的需求还要 2s 才过期，只看上报的速率会把「桶还满着」
误判成争抢。以桶的实际存量为准、并要求紧张持续一个周期，才把突发与持续超限区分开。

## 7. 需求估计

```
window  = now − measuredAt
current = arrived / max(window, 100ms)
current ≥ demand            → 采用 current          # 上升立即生效
current <  demand：
    window ≥ 100ms 且 demand × window ≥ 4 × avgCost → 采用 current   # 样本足够才承认下降
    否则                                            → 维持 demand
结果不超过 L
```

- 上报值不做衰减：衰减会让下降的实例长期高报需求，造成假的争抢，把突增实例卡在公平份额上。
- 「样本足够」的要求避免稀疏流量（例如每 200ms 一个请求）在 100ms 窗口里被误判为降到 0，进而退还额度、在争抢时被大流量挤占。

## 8. 退避

一次租约授予量小于申请量后：

| 情况 | 判断 | 效果 | 时长 |
|---|---|---|---|
| 额度真正紧张 | Lua 返回 `scarce` | 之后的请求不再等待，只能用透支空间 | 本实例公平份额低于需求时 100ms，否则按缺口 / L |
| 连必须满足的部分都没领到 | `grant < required` | 同上 | 按 `(required − grant) / L` |
| 只是预取没领满 | 其余 | 只暂停异步预取，请求仍可等待 | 按缺口 / L |

时长都夹在 20ms 到 500ms。两种退避分开，否则预取领不满会连带挡住真实请求的等待；
真正紧张时一律停止等待，否则每个请求都会去 Redis，形成频繁调用。

## 9. 透支

共享模式下每个服务在每个实例上的透支上限：

```
overdraft = min(L × 200ms, C / max(peers, 1))
```

- 用途：需求下降最多 200ms（响应窗口 + 扫描间隔）后才被发现，这段时间突增的实例从 Redis 领不到足额，靠透支撑过去。
- 只在两种情况下使用：服务在退避中；或紧急补货回来后仍不够。
- 请求只能使用剩余透支空间（`balance − cost ≥ −overdraft`）：大请求不能把欠账挖深。
- 欠账计入下一次租约申请量，长期速率仍等于 L；持续超限时欠账停在上限，照常限流。
- 所有实例同时透支到上限也不超过一个 C。

## 10. 故障与降级

### 10.1 健康状态

补货泵对 Redis 有三档判断：

| 事件 | 结果 |
|---|---|
| 租约成功且耗时 ≤ 25ms | 健康：余额不够时可以等一次补货 |
| 请求等待紧急补货超过 50ms | 变慢 |
| 租约成功但耗时 > 50ms | 变慢：Redis 能用但请求等不起 |
| 故障之后租约成功、但耗时 > 25ms | 变慢：Redis 恢复应答但还不够快，不再停在本地降级 |
| 租约调用失败 | 故障（原因 `closed` / `timeout` / `error`） |
| 距最近一次同步成功 > 1s | 视为故障（同步卡在一次慢调用里时也能自行切换） |

25ms 与 50ms 之间留迟滞，避免来回切换。新客户端从健康开始。

### 10.2 Redis 变慢

Redis 抖动（RDB fork、慢命令、网络重传）让一轮租约晚回来几十毫秒，并不说明共享桶没有额度。
旧实现在这里切到按实例平摊的本地降级，切流时接手流量的实例只有约 `L / 实例数` 的本地额度，限额之内也会被拒。
变慢时：

- 仍按共享额度记账，补货照常进行（包括异步补货与退还），只是请求不再等待。
- 余额不够时先欠着放行，欠账上限 `stallAllowance = min(C, 最近一次租约之后桶中的可用量 + L × 距那时的时长)`，
  不小于透支上限；从没拿到过可用量（冷启动恰逢 Redis 变慢）时按 C。额度真正紧张（处于退避）时仍只有透支空间。
- 欠账计入之后租约的必须满足部分，从共享桶中扣回。限额之内的流量对应的额度本来就在桶里，补货一回来就还上，
  不会多放行；只有共享桶确实已经空了才会多放行，每个实例至多一个 `stallAllowance`，长期速率仍是 L。
- 等待超时的等待者同样按这条规则放行：它们的需要已经包含在路上那一轮的申请里。

### 10.3 本地降级（故障时）

- 补充速率 `min(L, max(share, L / peers))`；还没拿到过 `peers` 时按 L。
  - `share` 让总量大体不变；`L / peers` 让故障期间流量转移过来的实例不被卡在旧份额上。总量至多约 2L。
- 本地容量 `C × 速率 / L`。
- 进入降级时保留余额（它们在 Redis 中已扣减过，欠账则先由本地补充还上）；从没领到过额度的服务从满桶开始（冷启动恰逢 Redis 卡住也不丢数据）。
- 回到共享模式时余额清零：本地补充出来的令牌在 Redis 中没有对应扣减。

### 10.4 配置问题

| 情况 | 行为 |
|---|---|
| 主配置没有 `redis` 段 | 处理器空转，等同于额度为 0 |
| `redis` 段非法 | 保留额度语义，每实例独立限流（`mode=local_only`） |
| 主配置结构损坏 / 额度非法 | 忽略该额度，处理器空转或不限流 |
| Redis < 5（脚本报错） | 租约持续失败，停留在本地降级 |

## 11. 生命周期

- **Factory**：装载配置；`redis` 段合法时建立客户端并启动补货泵。
- **Reload**：只替换额度索引与配置快照；Redis 连接参数变化时才换客户端与补货泵，并清空本地余额（换了 Redis 就换了共享桶）。配置不变的 Reload 不会重新发放满桶。Reload 不等待在途租约。
- **Clean / Stop**：停止补货泵并等在途租约结束（至多 1s），用一次批量调用归还共享模式下的全部正余额、删除本实例的需求记录（至多 200ms），再关闭客户端、清空本地状态。Collector 正常退出时，`Controller.Stop` 在 Receiver 停止、记录处理完之后调用 `pipeline.Manager.Stop`，后者只通知实现了可选接口 `processor.Stopper` 的处理器（目前只有限流器），其他处理器的退出行为不变。不归还的话，发布时退出的实例会把预取的额度带走，其需求记录还要 2s 才过期。Pipeline Manager 会把 Clean 过的实例直接装配使用，因此下一个开启限流的请求通过 `ensureRedis` 自愈重建客户端。
- 请求路径只读一次配置快照指针，不持有写者锁，Reload 与请求互不阻塞。

## 13. 保证与上界

| 场景 | 保证 |
|---|---|
| 任意时长 t | 全局放行 ≤ `2C + L × t`（共享桶一份，各实例透支之和一份），之后稳定在 L |
| 限额之内的流量转移、单实例突增 | 不丢数据；突增的请求至多多等一次 Redis 往返 |
| 宏观平均不变、流量瞬时到达 | 与理想的全局令牌桶一致；仅多个实例同一瞬间突发且平均负载达到额度时多拒约 1% |
| 实例全部退出、新实例承接流量 | 不丢数据 |
| 发布切流（部分实例退出、流量突发切到存量实例） | 不丢数据，按 100ms 窗口断言；正常退出时归还额度，直接退出也能接住 |
| 持续超限 | 总量稳定在 L；max-min 公平，不饿死 |
| 单个请求 > burst_bytes | 立即拒绝，原因可区分 |
| Redis 变慢（几十毫秒级抖动） | 请求不阻塞、不回退本地；限额之内的突增与切流不拒；超限时每个实例至多多放行一个 `stallAllowance`（≤ C），之后从租约中扣回 |
| Redis 故障 | 请求不阻塞，总量至多约 2L，恢复后立即回到共享 |

## 14. 指标

| 指标 | 用途 |
|---|---|
| `traffic_limiter_bytes_total{token, service_name, record_type, result}` | 谁被限了（原始逻辑字节） |
| `traffic_limiter_rejected_total{reason}` | `quota` 额度用完 / `exceeds_burst` 单请求超过 burst（需要调大配置） |
| `traffic_limiter_decisions_total{backend, reason}` | 判断时用的是共享额度还是本地降级；`redis / timeout` 表示 Redis 变慢、请求不等待；`local` 持续增长说明额度正在放大 |
| `traffic_limiter_lease_wait_total{result}` | 突增时等待补货的结果；`timeout` 增长说明 Redis 往返超过 50ms |
| `traffic_limiter_sync_total{result}` | 租约调用成败 |
| `traffic_limiter_mode{mode}` | 配置态：`disabled` / `local_only` / `shared` |

## 15. Redis 开销（每个实例）

| 场景 | 调用 |
|---|---|
| 无活跃服务 | 0 |
| 稳态 | 约 2 次/s（一次 EVAL 处理全部活跃服务） |
| 突增 / 需求下降 | 额外几次，合并成批 |
| 持续超限 | 每个受限服务每 100ms 至多一次，合并成批 |
| Redis 故障 | 2 次/s 探测 |
| 上限 | 1/RTT（同一时刻至多一个在途） |

每次 EVAL 对每个服务的开销为 O(该服务的存活实例数)（读需求表）。按单服务实例数 ≤ 50 设计。

## 16. 样例（L = 10KB/s，B = 10KB，C = 10KB）

1. **限额内突增**：10 个实例，C 从 0.5 突增到 8KB/s，其余共 1.8KB/s。C 余额耗尽 → 紧急补货（桶中可用约 8.6KB）→ 放行；之后异步补货与定时同步维持余额。不丢数据。
2. **负载均衡转移**：5/5/0 → 0/2/8（总量恰好 100%）。下降的实例 100ms 内被扫描发现，退还预取、上报新需求；这段时间突增的实例从桶里领到部分额度，其余靠透支（≤ 2KB）撑过去。不丢数据。
3. **持续超限**：A 8KB/s，其余 9 个实例各 0.5KB/s。进入公平模式，小实例拿满 0.5，A 约 5.5；A 的超出部分在透支用到上限后被拒，总量稳定在 10KB/s。
4. **冷启动**：10 个实例同时以 2KB/s 开始。各实例紧急补货，先到先得，随后进入公平模式；任意窗口不超过 `2C + L × t`。
5. **大请求**：12KB 超过 B，立即拒绝；3KB 而余额 1KB 且未退避：等一次补货，拿到即放行。
6. **Redis 抖动**：一轮租约卡了 80ms。等待者等满 50ms 后按欠账放行，之后的请求不再等待、余额不够时先欠着；
   那一轮回来后欠账还上，下一轮 ≤ 25ms 的租约恢复等待。限额之内不丢数据。
7. **Redis 卡死**：同上先按欠账放行；1s 没有同步成功（或租约报错）后切到本地降级。

## 17. 已知限制

- 单服务存活实例数很多（> 50）时，Lua 读需求表的开销线性增长，需要改为 O(1) 的计数方式。
- Lua 已在 Redis 执行但客户端超时，这次授予会丢失（关闭了自动重试以免重复扣减），只在真正断网时发生。
- 空闲实例手上至多保留一次预取量，下一次定时同步或需求下降扫描时退还。
- 本地降级期间单个请求大于本地容量 `C × 速率 / L` 时会被拒。
- Redis 变慢期间，若多个实例同时遇到超过容量的突发，每个实例都可能先欠到 `stallAllowance`，瞬时总放行理论上至多
  多出「实例数 × C」，之后从租约中扣回。只在 Redis 抖动与超限突发同时发生时出现。
- 多个实例在同一瞬间突发、且平均负载达到额度时，各实例的预取与透支欠账让它比理想的全局令牌桶多拒约 1%（80% 负载约 0.3%，60% 负载为 0）。
- 客户端批量发送时，`burst_bytes` 应按所有实例可能同时到达的最大批量设置；即使理想的令牌桶，突发超过容量也会被拒。
- 只支持 standalone Redis。
