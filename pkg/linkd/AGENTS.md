# Linkd 项目协作规范

## 适用范围

本文件适用于整个仓库。只有当某个子目录确实需要更严格或不同的规则时，才允许在该目录增加局部 `AGENTS.md`；局部规则不得削弱本文的安全、质量和领域边界要求。

协作说明、设计文档和提交摘要默认使用中文；Go 标识符、包名、配置键和外部协议字段使用英文并保持既有拼写。

## 项目背景与当前阶段

Linkd 是从 Kingeye 中拆分出的独立 Go 项目，计划探索告警接入、规范化处理、生命周期、丰富、存储和输出等能力在新系统中的合理边界。

项目当前处于早期开发和领域收敛阶段，尚未发布稳定版本或对外稳定 Go API。仓库已经实现部分领域对象、存储适配器、消息消费运行时和生命周期处理，但接入清洗、完整恢复、丰富和生产部署链路仍未闭合。现有文档使用 `alarm_collect`、`alarm_clean`、`alarm_event`、`alarm_lifecycle`、`alarm_enrich`、`alarm_sink`、`alarm_push` 等名称帮助讨论问题，但这些名称、模块数量、职责、依赖关系和处理顺序都不是最终结论，后续可以合并、拆分、重命名或调整。

早期开发阶段不把尚未发布的内部类型、配置字段、存储 schema 或草案协议视为默认兼容性边界。模型需要调整时，优先直接修改代码、测试和权威文档，不为未投入使用的旧形态增加兼容层、双写或迁移逻辑。只有已经明确版本化的外部契约、需要保留的真实数据或用户特别要求的升级路径，才单独设计兼容与迁移方案。

除非某项设计被明确标记为已确认并已有对应实现，否则默认把它视为工作草案，而不是必须照搬的领域模型、模块契约或目标目录结构。设计文档更不代表相关功能已经运行、部署或通过生产验证。

涉及现状说明时必须明确区分：

- 当前仓库中已经存在并经过验证的代码；
- 尚未定稿的领域设计、候选模块和职责假设；
- 技术调研、候选方案和待确认推导；
- Kingeye/KAC 中仍在运行的旧实现。

不得把旧 KAC 行为自动当成 Linkd 契约，也不得把 Linkd 规划反向描述成现行 KAC 行为。

## 权威资料与阅读顺序

判断问题时按以下顺序取证：

1. [实际代码](cmd/linkd/main.go)、测试、`go.mod`：判断当前真正实现了什么。
2. [根 README](README.md) 与 [对外使用和部署文档](docs/guides/README.md)：判断当前可运行、可交付和可运维范围。
3. [总体设计](docs/design/architecture.md)：了解当前对系统边界和处理流程的初步设想，不据此认定最终架构。
4. [功能模块文档](docs/modules/README.md)：了解候选模块的设计草案和待验证假设，不据此固定代码包或职责。
5. [术语与外部契约](docs/reference/README.md)：了解当前使用的统一语言和候选集成边界；只有明确确认并版本化的契约才具有稳定约束力。
6. [技术调研](docs/research/README.md)：仅作设计输入，不作为现行实现或最终契约的唯一依据。

当前设计草案没有对应实现不构成代码缺陷。文档与已有代码、已确认决策或外部契约发生实质冲突时，不得静默选择其中一方：先指出差异，再确认应修改实现、文档还是设计假设。缺少已确认设计的领域能力不得靠猜测补全关键契约。

## 代码结构

- `cmd/linkd` 保持为进程入口，不在入口文件中堆积可独立测试的业务逻辑。
- 尚未确认领域边界前，不按设计文档中的候选模块批量创建空包，也不要求 Go 包与文档章节一一对应。
- 新增包应服务于当前已实现的用例和清晰职责；当实现证据表明现有候选模块边界不合适时，优先调整设计，而不是为了符合草案制造额外转发层。
- 非公开实现优先放在 `internal/`。具体采用按领域、按用例、分层或混合结构，应在首批真实实现中根据依赖和变化边界确定，并同步记录理由。
- 只有至少两个真实消费者共享且不含领域语义的技术能力，才考虑提取共享技术包；不要预先假定必须存在 `internal/linkd` 或 `internal/platform`。
- 没有已确认的仓库外消费者前，不创建 `pkg/` 或公开 Go API。
- 禁止新增万能 `common`、`utils`、`helpers` 包；公共抽象必须有清晰语义、稳定边界和实际消费者。

## 依赖与模块边界

- 不预先把当前文档中的处理顺序固化成最终包依赖图；实现前应根据已确认用例、数据所有权和一致性边界重新核对依赖方向。
- 包之间不得形成循环依赖。跨边界协作使用窄接口，接口由消费方在其边界定义；避免为了“可能复用”提前抽象。
- 依赖通过构造函数显式注入，不使用隐藏的全局可变状态、服务定位器或包级初始化副作用。
- 一个包不得绕过另一个包的公开边界直接依赖其私有类型或内部实现；数据库表、缓存键等数据所有权在领域边界确定前逐项设计，不能仅凭候选模块名推断归属。
- 外部系统、存储和消息中间件通过端口隔离，但只有当事务、一致性、排序和恢复语义也被接口表达时，才能宣称实现与具体基础设施解耦。

## 领域设计状态与稳定工程原则

当前设计草案分别讨论了接入、清洗、事件、生命周期、丰富、存储和推送等关注点。这些文档用于暴露问题、术语和候选边界，不表示项目已经确定了七个独立模块，也不表示其中的对象、字段、状态机或职责不可调整。

- 实现领域能力前，先确认相关文档的状态、未决问题和本次真正需要支持的用例。
- 不以本文件作为领域 schema、状态机、消息格式或模块接口的定义来源；这些内容需要在设计评审和真实实现中逐步收敛。
- 如果实现需要偏离当前草案，应说明原因并同步更新设计材料，而不是增加兼容层维持尚未确认的抽象。
- 只有被明确确认的契约和已经由测试保护的行为才视为兼容性边界；其余领域设计允许演进。
- 嵌套、动作分型的 `KingeyeAlertEvent` 已废弃，不再作为目标模型或兼容边界。当前及后续事件模型统一以 `internal/domain.AlertEvent` 为演进基线；需要新增字段或调整语义时直接修改 `AlertEvent` 及其存储、消费者、测试和文档。

无论最终采用何种领域模型和模块划分，以下工程问题都必须被显式处理，但具体方案仍由对应设计和实现确定：

- 所有业务数据、状态、凭据、消息身份、锁、租约和缓存键都按 `bk_tenant_id` 或等价稳定租户作用域隔离；
- 重投、重试和进程恢复使用稳定身份实现幂等，不使用当前时间、随机数或进程内顺序作为业务身份兜底；
- 并发、队列、批次、载荷和重试都有硬上限，支持背压、超时、取消和优雅退出；
- 不记录 token、密钥、完整凭据或未经脱敏的敏感 payload，错误和日志必须保留定位上下文但避免泄漏数据；
- 使用 Kafka 时，顺序、offset 提交、事务边界和失败恢复必须显式设计，不能以“消息能消费”代替端到端可靠性证明。

## Go 编码规范

- Go 最低版本以 `go.mod` 为准，当前为 Go 1.26.7。项目是全新开发，不为兼容旧 Go 版本降低语言或标准库基线。
- 所有 Go 文件使用 `gofmt`；不维护与 `gofmt` 冲突的手工排版规则。
- 包保持职责单一，名称简短明确；导出符号只在确有跨包消费者时创建。
- 接口优先小而专一，通常由消费方定义；函数返回具体类型，除非返回接口具有明确替换或隔离价值。
- 阻塞操作、外部 I/O 和可取消的长时间操作必须接收并传播 `context.Context`，通常作为第一个参数；不要把 Context 保存到结构体字段。
- 错误必须被处理或返回。增加语义时使用 `fmt.Errorf("...: %w", err)` 保留错误链，调用方使用 `errors.Is/As` 判断；库代码不得用 `panic` 处理可恢复错误。
- 资源必须在成功获取后及时释放，HTTP body、数据库 rows、事务、文件、goroutine 和 channel 都要覆盖正常与异常路径。
- 包职责、导出符号、公共字段和关键实现的注释遵循下述“代码注释规范”。
- 优先使用标准库。新增第三方依赖前必须说明必要性、维护状态、许可证、升级成本和标准库/既有依赖为何不足；不得为简单能力引入大型框架。

## 代码注释规范

注释的目标是让维护者理解代码无法直接表达的契约、约束和设计原因，而不是追求注释数量。能通过准确命名、拆分函数、收窄接口或测试清楚表达的内容，优先改进代码本身。

- 每个生产包都应有包级注释，简要说明职责和关键边界；导出类型、函数、方法、常量、变量和需要对外理解的公共字段应有符合 GoDoc 的注释。GoDoc 通常以被注释的标识符开头，并说明可观察行为，而不是只把标识符翻译成中文。
- 未导出符号不要求逐一注释，但承载领域规则、协议约束或非显而易见流程的实现必须说明。尤其是租户隔离、身份生成、状态转换、数据单位、空值语义、边界条件和兼容行为，应在最接近实现的位置写清楚。
- 并发、事务、幂等、排序、offset 提交、重试、背压、超时、取消、租约和故障恢复逻辑必须说明“为什么这样做”、依赖的不变量，以及违反约束可能造成的后果；不要只复述加锁、循环、判断或赋值动作。
- 函数存在重要副作用、失败后可能部分生效、返回值带有特殊语义，或调用顺序有要求时，注释必须明确这些调用方契约。无法由函数签名表达的输入限制、输出保证和错误分类也应写清楚。
- 注释默认使用中文，Go 标识符、配置键和协议字段保持原始英文。注释应紧邻所说明的代码；修改行为时同步更新相关注释，过期注释与错误实现同等处理。
- 不保留被注释掉的旧代码，不写逐行翻译代码的注释，不把尚未确认的设计设想写成既有事实，也不在注释中记录密钥、完整凭据或未经脱敏的业务 payload。
- `TODO`、`FIXME` 只用于明确且可执行的后续事项，至少写明当前限制、完成或删除条件；已有跟踪项时附上编号或链接。禁止只写“后面优化”“临时处理”等无法验收的占位注释。

以下示例只说明注释写法，不定义 Linkd 当前的领域契约：

```go
// NormalizeEvent 按已确认的映射规则规范化输入事件。
// 返回 nil error 仅表示规范化完成，不表示事件已经持久化或投递。
func NormalizeEvent(input RawEvent) (Event, error) {
    // ...
}
```

```go
// 必须按分区提交连续成功的最大 offset；跳过中间失败消息会使其在
// rebalance 后无法重放，破坏至少一次处理语义。
commitOffset := highestContiguousOffset(results)
```

下面的注释没有提供代码之外的信息，应删除或改写为约束和原因：

```go
// 遍历消息。
for _, message := range messages {
    // 设置租户 ID。
    event.TenantID = message.TenantID
}
```

## 测试规范

- 单元测试与被测包放在一起，领域规则优先使用表驱动测试并让失败用例具有可读名称。
- 每次行为修改至少覆盖正常路径、边界输入和明确失败路径；修复缺陷时先补充能复现问题的回归测试。
- 领域测试场景必须来自已确认需求和当前实现。确定性、幂等、身份冲突、状态转换、租户隔离、乱序、失败重试和恢复是现有草案提出的重点候选风险，不在需求尚未定稿时自动视为最终验收规则。
- 存在 goroutine、锁、channel、并行消费或共享状态的代码必须包含取消、退出和并发场景测试，并通过 race detector。
- 依赖 Kafka、数据库或其他外部服务的测试必须明确标识为集成测试，不得让普通单元测试隐式依赖开发者本机环境。
- 不用提高覆盖率数字代替关键不变量测试；测试断言应验证可观察行为，不绑定无关内部实现。

## 文档维护

- 文档结构和分类以 [文档中心](docs/README.md) 为准，同一内容只保留一个权威位置。
- 新增或修改领域术语时先更新 `docs/reference/glossary.md`。
- 跨模块流程、系统边界和重要取舍更新到 `docs/design/`；单模块职责、模型和行为更新到 `docs/modules/`；外部协议更新到 `docs/reference/contracts/`。
- 调研必须记录时间、版本或源码快照、证据、结论和未决问题；结论被采纳后同步更新设计或模块规格。
- 变更代码时检查相关文档是否需要同步，变更文档路径时检查所有相对链接和锚点。
- 未执行的测试、未完成的实现和未验证的运行行为必须明确说明，不得写成“已通过”“已支持”或“已上线”。

## 质量门禁

代码改动提交前运行：

```bash
make check
```

`make check` 必须是只读门禁，依次检查格式、普通测试、`go vet`、竞态测试和静态分析。`staticcheck` 由 `golangci-lint` 统一执行，不重复调用独立二进制。

静态分析要求 `golangci-lint` v2，当前验证基线为稳定版 v2.13.2，并确保支持 Go 1.26。升级工具版本或调整 linter 集合时必须显式更新配置，并重新运行完整门禁，不能依赖开发者本机的隐式默认值。

需要格式化时显式运行：

```bash
make fmt
```

只有 `make fmt` 可以改写源码。文档类改动至少检查受影响的本地链接和锚点；修改本文件、Makefile 或 lint 配置时仍应执行完整 `make check`。任何检查因环境或外部依赖未运行时，交付说明必须写明具体阻断原因。

## Git 与交付规范

- 保留用户已有改动，不覆盖、不回滚、不顺手清理任务范围外的文件。
- 未经用户明确要求，不创建 commit、不推送、不改写历史，也不执行破坏性 Git 操作。
- 提交信息使用 Conventional Commits：

```text
<type>(<optional-scope>): <中文或英文摘要>
```

- `type` 只使用 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`build`、`ci`。
- 一个提交只表达一个可解释的目的；行为变化、重构和纯格式化不要混在同一提交中。
- 交付时说明实际修改、验证命令与结果、未验证事项和剩余风险；不要用文档或静态检查通过替代运行时验证结论。
