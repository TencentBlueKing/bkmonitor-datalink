# 合并持久批次池历史测量（2026-10-16）

本页仅保留旧方案与性能证据。用户已确认退役跨进程分发及批次中间存储；这里的设计、命令与测试结果不代表当前实现。现行实现见[单进程内存批次](../../design/policy-runtime-scaling.md#1210-单进程内存批次与直接回报)。

### 12.5 单组跨进程批次池（用户明确的扩展目标）

上一节仍只减少每个串行块的成本，不能满足同组多个批次并行的要求。目标模型是 N 个成员按 B=128 形成待处理批次，主控制面和独立合并 Worker 共同领取，单进程最多 M 个批次在途。理想成员阶段耗时约为 ceil(ceil(N/B)/M) × 单批耗时；阶段协调、固定启动开销和下游饱和另计。`concurrency` 限制在途批次数，不能继续解释成单个批次内只执行 M 个成员。

- 冻结成员后按固定身份持久化小批记录；沿用现有策略存储和 Redis 租约，不新增消息系统。每批只包含本批成员、不可变关系摘要、进度与 CAS token，执行不读取完整 N 成员文档。
- 多进程扫描同一待办集合，以批次键取得已有 Redis 租约，再实时读取批记录。成员仍复用 fingerprint 锁及自己的 CAS；批内成功成员记录完成，CAS 冲突或其他失败成员留在本批待办，后续只重试未完成项。进程退出或租约过期后批记录仍可领取，不依赖进程内队列保活。
- 整组窗口锁仅串行准备阶段和最终状态切换，不包住成员批次。引用完整、成员完成、父放行保留阶段屏障；组级最终确认通过批记录的实时读取完成，不能用 ES 搜索暂时漏掉待办来判断全组成功。
- 并行批次不再竞争同一个 Decision/Relation 进度 CAS。它们各自确认自己的记录；组级协调一次汇总成员结果并更新关系，后续父准入仍实时检查父/成员状态。父提前结束时建联批次停止新增关系，结束阶段独立批次负责清理。
- 验收必须包含至少两个独立控制进程共同处理同一组、同批竞争、部分 CAS 失败、成功后确认响应丢失、领取进程退出后接管、父提前关闭，以及 B/M 扩大后的批耗时与总耗时对照。单进程 goroutine 并发测试不能替代跨进程验收。

主控制面仍为单主；第二个 `control-plane` 会被调度器拒绝。当时新增独立成员执行进程 只装配批处理所需来源、策略、等级、仓储和 Hook，不取得来源调度资格，不启动管理 API。结束阶段在批次池追加一个组级收尾待办，使用窗口锁核对实时批记录；它不阻塞其他成员批，也不必等待活动关系的 30 秒复查周期。

历史双进程测试分别断言两个执行进程都有成功成员批写；该部署和测试模式现已退役。

### 12.7 跨进程验收与扩展边界

同一最终二进制再运行四组“主控制面 + 独立成员执行进程”，每个进程并发 8 批，全部通过成员/引用/恢复/动作校验：

| 后端 / 成员数 | 创建完成 | 恢复清理总计 | 主控制面 / Worker 成功成员写入批数 |
| --- | ---: | ---: | ---: |
| ES / 5,000 | 12.430 s | 14.461 s | 24 / 16 |
| ES / 10,000 | 17.787 s | 36.690 s | 38 / 41 |
| MySQL / 5,000 | 6.199 s | 23.531 s | 24 / 16 |
| MySQL / 10,000 | 9.346 s | 45.363 s | 41 / 38 |

两个进程确实共同执行同一组，各自批数之和为 40 / 79。额外进程没有带来稳定的倍数提速；
两个进程合计的 ES 业务批写均值为 24.40 / 24.28 ms，比单进程 17.81 / 17.44 ms 上升。
MySQL 双进程均值为 58.68 / 33.09 ms，样本波动更明显。这些仍是应用仓储方法耗时，不是纯服务端 SQL/ES 时间。
因此 `ceil(N/B)/M × T_batch` 中的 T_batch 在提高并发后并未保持不变，整组还有固定阶段和可见性等待；
本轮不能承诺继续增加 M 会等比例降低总时间。代码已去掉窗口串行和页级完成屏障，空闲名额会继续取下一批，后续扩容需要结合实际后端容量。

最终实现的故障边界已经覆盖：同组不同批并行、未完成项重试、确认提交前失败、确认响应丢失、取消、父提前关闭与全组清理；
真实 ES/MySQL 的局部进度 CAS 竞争、固定字段/null 保留与已完成批次 create-only 重放通过；真实 MySQL 128 成员批写只产生一次 UPDATE。
真实 Redis 子进程被强制终止后，同批在租约到期后可重新领取，另一批不被该组的旧批锁阻塞。该用例使用独立测试前缀及缩短的测试租期，不能将其一秒接管时间解释为生产默认值。

最终完整 `make check` 通过；新增池内故障用例又单独通过 race，最后 lint 为 0 issues。
最终代码的真实组合合并与策略准入 E2E 两后端均通过：组合场景各校验 11 条预期 KAC 动作消息，准入场景各校验 6 条，均无定时/解除成员误发动作。
容量、功能回归使用独立 ES 索引、MySQL 数据库、Redis 前缀和 Kafka topic，测试结束清理本轮资源；未部署或修改生产环境。

### 12.8 并发扩展诊断（2026-10-16）

本节记录定位和对照试验过程；最终保留的行为和验收结论见 12.9。

本轮先测量再优化，不从仓储方法均值推断数据库饱和。验证分三步：

1. 固定 B=128，在同一环境比较 1×8、2×4 和 2×8，区分进程数与总并发。批内记录身份读取、来源读取、租约准备、锁内读取、变更准备、CAS、输出、日志、完成确认、缓存和释放的墙钟时间；成员执行槽等待单独计量，不能将并行成员累计时间相加当作批耗时。
2. ES 拆分连接获取、请求发送、首字节、读响应、解码，并记录 Bulk 返回的 `took`；MySQL 拆分事务开始、版本锁定、UPDATE、COMMIT，并观测连接池累计等待；记录批次锁忙、空转及池内排队，区分调度等待与执行。所有指标只使用固定阶段标签，不携带成员或租户 ID。
3. 只针对有证据的瓶颈改动，保留 fingerprint 租约、独立成员 CAS、稳定输出身份与失败重试。使用相同负载重跑 5,000/10,000，并执行并发/失败测试。整组冻结、阶段轮询、父动作可见性单列，不放进 `N/B/M` 的成员吞吐比较。

首轮 5,000 成员实测（相同观测二进制，未优化执行流程）：

| 后端 | 1×8 单批均值 | 2×4 单批均值 | 2×8 单批均值 |
| --- | ---: | ---: | ---: |
| ES | 214.27 ms | 215.21 ms | 314.91 ms |
| MySQL | 147.64 ms | 146.88 ms | 215.38 ms |

相同总并发下进程拆分影响很小；总并发增加后单批变慢主要发生在成员执行阶段。ES 的 HTTP 获取连接均值低于 0.1 ms；MySQL 连接池等待计数为 0，事务开始约 0.19→0.31 ms、版本行锁查询约 1.50→1.91 ms、UPDATE 约 7.88→8.48 ms、COMMIT 约 2.47→4.27 ms（两个写阶段合计 80 个事务的均值）。ES 两次成员写的服务端 `took` 为 7.81→9.71 ms。不能用应用 CAS 方法总时长代替服务端执行时间。

ES 批内输出/完成缓存墙钟分别从 43.70/27.65 ms 升至 67.40/54.19 ms；MySQL 从 37.14/19.20 ms 升至 53.24/29.15 ms。全局成员执行名额被每批 128 个准备、输出、缓存 goroutine 反复争抢，多个批次放大等待和唤醒；Redis 大量等待集中在批尾 128 个租约同时归还，累计等待不是串行墙钟。双进程批锁忙只有 ES 40 次合计 13 ms、MySQL 77 次合计 49 ms，不是主要损耗。

据此先做局部优化并对照验收：租约先取得执行名额再启动持有 goroutine；批内准备直接循环，不与其他批的 I/O 争抢成员名额；输出/缓存使用有界工作 goroutine，不为全部成员同时建立等待者；已形成的 MySQL 多行日志批直接 INSERT，避免再次进入自动合批器后等待其他批。连接池、租约和 CAS 预算保持原值。额外保存逐批 debug 起止时间，计算成员执行区间，消除一秒状态轮询对吞吐比较的干扰。

进一步细分发现 MySQL 的 `member.cache_exec` 实际为零（该后端使用 NoopRecentAlertCache），但 `batch.cache` 仍可达十几毫秒，全部来自不必要的成员名额排队。MySQL 完成确认后直接返回，不为该空缓存步骤申请 I/O 名额；ES 仍保留完成 token 的缓存写入。

并发编排的试验没有通过性能验收：ES 5,000 实际成员区间由 1.108 s 增至 1.305 s。成员排队累计数虽然下降，批内输出却从约 40 ms 增至 93 ms。因此撤回准备循环、租约启动次序和有界工作 goroutine 的试验，保留原编排。不能把排队样本数量减少当作吞吐提升。

最终改动改为减少真实 I/O：完成确认后的 ES 缓存按来源分组，每组使用一次 Redis pipeline 写入独立 SET，仍使用各来源原有 key/TTL 与各成员已确认 token；任何单项失败独立返回，终态缓存保留原修复规则。来源混合时不共用错误前缀。MySQL 的空缓存步骤不排队；多行日志保持直写。指纹锁、业务 CAS、完成确认 CAS、输出顺序和进程执行预算均保持原值。

完成缓存 pipeline 的进一步观测显示物理调用均值约 2.2 ms、整个缓存阶段约 19 ms，差值主要是旧单成员名额等待。显式缓存批因此直接使用已有批次并发预算和 Redis 连接池，同批来源顺序提交，不再进入单成员名额队列。回归用例覆盖成员名额占满时显式缓存批仍能完成。

同样的门槛还影响批次来源读取：MySQL 10,000 的来源查询实际均值 0.74 ms，批次来源阶段却为 17.80 ms。`eventsource/storage` 已有独立的 8 连接上限，批次去重后的来源查询因此直接使用来源仓储，不再等待 Alert 成员 I/O 名额；仍逐批读取当前发布版本，不引入过期缓存。

独立来源读取试验同样未获得稳定吞吐收益：来源等待减少后，等待转移到租约准备/成员准备，部分样本实际区间反而增加。该试验撤回，来源查询继续沿用原成员预算；最终保留缓存显式 pipeline、缓存批脱离单成员队列、MySQL 空缓存跳过与日志直写。最终验收使用已完成全部 8 个容量子用例的 `linkd-profile-final2-20261016` 生产二进制；就绪观测的 MySQL 接口适配修正仅在测试程序中。

### 12.9 最终保留改动的实测结论

环境为同一台本机、Go 1.26.7、ES 7.17.7（4 CPU / 4 GiB）、MySQL 8.4.10（4 CPU / 4 GiB）、Redis 7.2（1 CPU / 1 GiB）。B=128；1×8 为单控制面 8 批，2×8 为控制面与独立成员执行进程 各 8 批。没有修改 ES refresh、数据库持久化或指纹锁/CAS 规则。

**实际成员执行区间**从第一个 `memberWave` 开始读取到最后一个成员批归还租约，由两进程 debug 起止日志合并计算；不包含裁决/冻结、父构建、关系引用阶段、批次发现与最终搜索可见性。5,000 / 10,000 分别为 40 / 79 个成员批。

| 后端 / 成员数 | 改前单进程 | 最终单进程 | 改前双进程 | 最终双进程 |
| --- | ---: | ---: | ---: | ---: |
| ES / 5,000 | 1.108 s | 1.146 s | 0.904 s | 0.883 s |
| ES / 10,000 | 2.221 s | 1.987 s | 1.764 s | 1.754 s |
| MySQL / 5,000 | 0.873 s | 0.811 s | 0.703 s | 0.719 s |
| MySQL / 10,000 | 1.867 s | 1.772 s | 1.548 s | 1.529 s |

最终单批平均耗时和实际并发：

| 后端 / 成员数 | 单进程批均值 | 双进程批均值 | 双进程有效 / 峰值并发 |
| --- | ---: | ---: | ---: |
| ES / 5,000 | 212.55 ms | 285.18 ms | 12.92 / 16 |
| ES / 10,000 | 188.64 ms | 312.27 ms | 14.07 / 16 |
| MySQL / 5,000 | 145.66 ms | 233.15 ms | 12.97 / 16 |
| MySQL / 10,000 | 167.28 ms | 272.90 ms | 14.10 / 16 |

有效并发 = 各批累计耗时 / 实际执行区间；它包含尾批影响，不能等同于配置上限。双进程确实达到 16 批同时执行，未被组锁串行化。最终双进程相对单进程的区间改善约 11%–23%，没有达到两倍。与改前相比，部分场景小幅改善，ES 单进程 5,000 和 MySQL 双进程 5,000 有小幅反向波动，不能声称整体稳定显著提速。

| 阶段 | ES 单 | ES 双 | MySQL 单 | MySQL 双 |
| --- | ---: | ---: | ---: | ---: |
| 身份批读 | 24.43 | 31.72 | 9.93 | 11.03 |
| 来源读取（含成员名额等待） | 17.82 | 40.79 | 17.80 | 25.41 |

| 变更准备（含名额等待） | 24.52 | 39.92 | 7.19 | 13.66 |
| 业务批 CAS | 17.40 | 23.71 | 26.28 | 39.19 |
| 逐成员输出 | 38.89 | 75.22 | 36.64 | 60.80 |
| 日志批写 | 12.82 | 15.60 | 32.74 | 64.35 |

完成缓存的 ES 单进程 5,000 均值从 31.18 ms 降至 1.99 ms，实际 pipeline 41 次；同样大小的普通单项写原先需要约 5,000 次调用。命令数仍随成员数增加，减少的是客户端往返。MySQL 的空缓存阶段为零。其他阶段仍有等待转移和存储延迟波动，不能把一个阶段节省的时间直接相加当作总提速。

主要结论：

- ES HTTP 取连接通常低于 0.1 ms；告警 MySQL 连接池 WaitCount 为 0。SQL 版本锁定查询和批锁忙的实测耗时较小，未显示它们是主瓶颈。Redis 连接池等待集中在逐成员租约归还；并行等待总和不能当作串行墙钟。

- 当前仍逐成员执行依赖索引、变更发布、输出前缓存和指纹租约。不同批共享成员执行名额，因此提高批并发会增大单批等待；ES 的两次完整批读还包含客户端解码/规范化，仓储方法总耗时不能全算到服务端。

- `ceil(N/B)/M × T_batch` 只适用于成员阶段且 T_batch 近似不变；增大 M 后 T_batch 已明显上升。5,000 只有 40 批，16 并发还存在尾批利用率损失。
