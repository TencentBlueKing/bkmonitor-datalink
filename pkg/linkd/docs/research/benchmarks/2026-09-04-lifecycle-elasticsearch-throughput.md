# Lifecycle 与 Elasticsearch 吞吐压测

测试日期：2026-09-04～2026-09-06。

## 1. 主要结论

- **归档等待和 Stream 裁剪不足是早期的明确限制。** 移除归档的 refresh 等待、增加连续裁剪后，
  Stream 可围绕软上限收敛，但 Lifecycle 在持续输入下仍会降速。
- **增加 ES 内存没有单独解决降速。** 2 GiB 扩到 4 GiB 后，文件缓存压力减轻，Lifecycle 仍从约
  800/s 降到 360～450/s；不能把问题全部归因于内存不足。
- **真正的大批次改善了有效写入吞吐。** 调整合批调度、分离读写队列并匹配调用并发后，平均每批
  79.35 个写操作，3 分钟窗口完成 937.3 Events/s，Signal lag 为 0～1。
- **分区尾部慢是另一类问题。** Kafka 长 fetch 与分区暂停/恢复叠加，产生约 5 秒的拉取周期；
  定向对照将恢复后的等待从约 4.8 秒降到了毫秒级。

937.3/s 包含历史积压追赶，且只覆盖短窗口，不代表长期可持续容量。各轮环境和改造不同，
本报告不据此给出生产配额或“某规格 ES 必然支持多少 Events/s”的映射。

## 2. 测试条件与指标口径

### 2.1 环境与负载

| 项目 | 条件 |
| --- | --- |
| 运行形态 | 单节点 all-in-one；共享 macOS/arm64 宿主机，Apple Container 虚拟块设备 |
| Elasticsearch | 7.17.7；2 vCPU；容器内存 2 GiB 或 4 GiB，heap 按轮次注明；零副本 |
| Redis | 7.2.16；1 vCPU / 512 MiB；AOF 关闭 |
| Kafka | 3.9.1；2 vCPU / 1 GiB；两路输入，每路 3 个分区、单副本 |
| 输入分布 | infra/service 新告警数量约为 1:2 |
| 告警模型 | 周期 1 秒，平均存活 20 个周期，重复投递比例 20%，每个新告警使用独立 fingerprint |

稳态下，每个新告警约产生一次 triggered 和一次 resolved，因此本模型的换算为：

```text
Events/s ≈ 新告警数/分钟 × 2 × 1.2 ÷ 60
```

600 Events/s 对应两路合计约 15,000 个新告警/分钟，800 Events/s 对应约 20,000 个。
该换算不适用于任意生产负载。

初始 Lifecycle 并发为 8。Cleaner 两路分别使用 4/8 个 worker、64/128 条批次和 1/2 个并行批次；
单分区在途上限为 256，恢复阈值为 128。后续轮次只在注明时改变相关参数。
R1～R5 使用 2 GiB ES 容器、512 MiB heap；R6 将 heap 调为 1 GiB，R7 起容器内存为 4 GiB。

### 2.2 如何解读结果

- 表中的吞吐是 Lifecycle 完成的 Events/s；目标输入速率、完成速率和 ES 文档操作数不是同一指标。
- Signal 是 Mailbox 的调度引用，两者积压不能相加当作未处理 Event 总量。
- ES translog 是已执行写入的恢复日志，不是待执行请求队列。
- 批次大小按 ES 文档操作计数，不按 Event 计数；一个 Event 可能依次产生多类写入。
- 早期部分 Lifecycle 延迟混用了 Handler 和 Processor 口径，本报告不使用这些值做跨轮比较。
  大批次结果中的 Event 延迟仅按 Processor accepted 计算，Bulk 耗时不包含入队等待。
- 持续输入时还需观察 Kafka/Signal 是否增长、归档是否追平、Stream 是否收敛及错误率。
  短窗口追平、停流后排空，均不等同于长期稳定。

## 4. 各项改进的效果与证据

### 4.1 取消归档 refresh 等待，增加 Stream 连续裁剪

**改进前：**

- History create 和 Active delete 使用 `refresh=wait_for`。归档批次平均约 4.92～4.95 秒，
  满批 1,000 条对应约 200 Alerts/s。
- 600 Events/s 负载约产生 250 个终态 Alert/s，超过上述归档速度。
- Stream 每 60 秒最多裁剪 10,000 条，理论上限约 166.7 entries/s；440/s 测试中，
  Signal 新增约 357 entries/s，长度仍会增长。

**改进：** 归档改为 `refresh=false`，冲突通过 realtime 读取核对；Stream 每轮在总预算内连续裁剪，
每批重新检查所有 Group/PEL 的安全边界，默认周期缩短为 10 秒。

| 指标 | 改进前 | R5 改进后 |
| --- | --- | --- |
| 归档 | 满批耗时接近固定 5 秒 | 不再受固定 refresh 等待限速；累计归档 128,802，无归档失败 |
| Stream 裁剪 | 每轮最多一次，追不上新增 | 累计新增 247,101、裁剪 150,000，长度 97,101 |
| Lifecycle | 600/s 后程降至约 508/s | 后程仍降至约 326/s |

**结论：** 改造解决了已识别的后台任务限制，但没有解决全部性能问题。
不能根据“归档等待已移除”推断 Lifecycle 必然稳定。

### 4.2 查询目标修正、归档平滑与内存对照

R6 将 Active lookup 限定到 Active alias，终态恢复查询使用 Active 与 History；
归档由 30 秒/4 worker 调为 5 秒/单 worker，并将相关索引 refresh 统一为 5 秒。
归档约 333～368 Alerts/s 时，terminal backlog 仍保持在调度窗口量级，未成为这一轮的持续积压源。

| 阶段 | R6：2 GiB 容器 / 1 GiB heap | R7：4 GiB 容器 / 1 GiB heap |
| --- | --- | --- |
| 前约 3 分钟 | Lifecycle 约 795～799/s | Lifecycle 约 794～799/s |
| 后程 | 曾降至 308.6/s，存在波动 | 多个窗口约 360～450/s |
| 文件缓存 | 典型样本约 0.62 GiB；10 秒内 842 次 file refault、28 次 major fault | 典型样本约 2.31 GiB；降速阶段 refault/major fault 未持续增长 |
| JVM | 未见 Old GC | 未见 Old GC |
| ES write rejected | 0 | 0 |

**结论：** 2 GiB 下存在文件缓存压力，但扩大容器内存后仍会降速，因此内存不足不是充分解释。
同期多类 ES 操作的延迟都上升，而 Lifecycle 只有有限数量的同步请求链，积压可以先出现在
Signal/Mailbox，不需要先填满 ES write queue。

R6 累计约 15.03 GiB block write、63.55 秒 merge、14.35 秒 merge throttle；
R7 分别约 12.03 GiB、48.04 秒、8.74 秒。这些数据说明存在更新、删除和后台合并成本，
但**累计写入量、平均带宽或累计 I/O time 不能单独证明 SSD 饱和，也不能证明 fsync 是唯一根因**。

### 4.3 AlertLog async 降低同步写成本，但没有消除拐点

R8 仅调整 AlertLog durability；Event、Active、History 仍使用 `request`。
与 R7 相近测试阶段相比：

| 阶段 | AlertLog request：Lifecycle | AlertLog async：Lifecycle |
| --- | ---: | ---: |
| 约第 4 分钟 | 484.5/s | 805.0/s |
| 约第 5 分钟 | 417.4/s | 659.5/s |
| 约第 6 分钟 | 392.8/s | 415.2/s |

async 组早期 AlertLog append 平均约 0.65～0.71ms，后程升至约 1.73ms。
30 秒高频采样中，ES write queue 最大 1、rejected 为 0，仍未出现持续的服务端写队列积压。

**结论：** 减少 AlertLog 同步点延后了降速，但剩余串行读取、CAS 和其他写入仍有限制。
这支持继续优化请求形态，而不是仅增加 heap 或扩大 ES write queue。

**代价：** async durability 下，异常故障可能丢失最近一个同步周期内已返回成功的 AlertLog，
不能把该配置当作无损的性能优化。

### 4.4 合批参数必须与实际就绪操作匹配

合批覆盖 Event result CAS、Alert CAS、Alert create、AlertLog create。
同一 Event 的依赖写入仍逐步等待结果，不能提前提交后续日志或终态。

初始参数扫描结果如下。C 为 Lifecycle 并发，P 为批次执行并发，W 为最大等待时间。
R9 开启组及下表使用单批 32 项、4 MiB 上限；R9 初始 P=2、W=2ms。
各组统计窗口为 30～60 秒，复用了累积数据，输入消化速度及缓存状态并不完全相同；
它们用于定位，不是严格容量对照。

| C / P / W | Lifecycle Events/s | 平均写操作/批 | Bulk 执行均值 | 写批次排队均值 |
| --- | ---: | ---: | ---: | ---: |
| 32 / 4 / 2ms | 357.7 | 5.48 | 5.20ms | 10.62ms |
| 32 / 4 / 0ms | 372.6 | 2.06 | 3.14ms | 8.91ms |
| 64 / 4 / 0ms | 359.4 | 2.11 | 3.60ms | 28.21ms |
| 64 / 8 / 0ms | 445.5 | 2.09 | 6.14ms | 15.30ms |
| 64 / 8 / 2ms | 540.1 | 6.35 | 6.50ms | 13.35ms |
| 32 / 关闭合批 | 478.5 | — | — | — |

增加调用并发不一定提高完成量：32→64、P=4/W=0 时吞吐没有提高，排队时间反而增加。
取消等待也不一定更快，因为批次会退化到约两条操作。

此外，调度器在首项期限已过时，让 timer 与非空队列竞争，可能把 32 个已就绪操作拆成
12～20 个请求。修正为优先合入已就绪操作后：

| C / P / W | Lifecycle Events/s | 平均写操作/批 | Bulk 执行均值 |
| --- | ---: | ---: | ---: |
| 32 / 2 / 2ms | 367.4 | 7.02 | 4.73ms |
| 64 / 8 / 2ms | 532.1 | 9.77 | 7.24ms |

**结论：** 修复提前切批是必要的，但仅修复这一点仍未达到 800/s；
需要同时让足够多的独立写操作进入批次。

### 4.5 大批次验证：从数条操作增至约 80 条

R10 在前述修正上进一步：

- 将 realtime 读取放入独立队列，不占写阈值，也不等待写批次期限。
- 使用 Lifecycle 并发 256、单批上限 100 个操作、最长等待 100ms、最多 32 批并发。
- 保留单批 4 MiB、调用数和请求大小上限，以及原有逐项失败、幂等和 ACK 边界。

| 指标 | 3 分钟结果 |
| --- | ---: |
| Lifecycle 完成量 / 平均吞吐 | 169,254 / 937.3 Events/s |
| Cleaner 平均吞吐 | 938.0 Events/s |
| Lifecycle 写 Bulk 数 / 写操作数 | 7,114 / 564,522 |
| 平均写操作/批 | 79.35 |
| Bulk 执行 / 首项排队均值 | 7.69ms / 25.73ms |
| 每完成 Event 的 Lifecycle 写 Bulk 数 | 0.042 |
| Event accepted 平均 / 末个一分钟窗口 P99 | 92.63ms / 392.46ms |
| Signal lag | 0～1 |
| Repository failure / retry / ES rejected | 全部 0 |
| Stream 长度 | 97,745～106,178，持续裁剪，非单调增长 |

停流后 Kafka、Signal、Mailbox 与 terminal backlog 均排空，Stream 回落到 96,695。

**结论：** 单个 Bulk 的执行时间由数毫秒增至约 7.7ms，但承载的操作从个位数增至约 80，
请求成本得到更充分的摊销。同一 ES 规格下，短窗口完成速率能够超过 800/s。
不过，这轮同时改变了调度、读写队列和并发，不能把全部收益归给单一参数；
增加聚合等待还需关注低流量延迟。

为减少手调不匹配，后续将批次操作数、等待时间和执行上限改为从 Lifecycle 并发自动推导。
并发 256 仍对应本轮有效参数；其他档位尚无独立的容量验证。
具体规则见[配置指南](../../guides/configuration.md#lifecycle-elasticsearch-合批)。

## 5. Kafka 单分区尾部慢的定向验证

### 5.1 现象与改进

吞吐测试末尾曾仅剩一个 partition 积压，Cleaner 约 51.2 条/秒，每分钟 pause/resume 各约 12 次。
单分区在途上限 256，`256 / 5s = 51.2/s` 与实测速率吻合；同期 ES 批写平均约 27ms，
Lifecycle 单 Event 平均约 12.6ms，不足以解释秒级拉取空档。

改进是将 Kafka `FetchMaxWait` 从客户端默认的 5 秒显式缩短为 100ms，
不改变分区在途上限、暂停/恢复滞回或连续 ACK。

### 5.2 对照数据

测试使用同 broker 的三个分区，仅向 partition 1 写入 1,024 条有序消息，停止生产后再消费。
每收到并确认 256 条，暂停该分区 200ms；暂停期间继续拉取其他空分区，再测量恢复后的等待。

| fetch 等待 | 三轮 1,024 条处理耗时 | 恢复到下一批到达 |
| --- | --- | --- |
| 5s | 15.038s / 15.041s / 15.033s | 九次均为 4.805～4.811s |
| 100ms | 0.647s / 0.655s / 0.651s | 九次为 7.52～16.34ms |

耗时从首批到达开始计算，包含三次固定的 200ms 暂停，不包含消费组首次分配时间。
三轮均保持消息顺序、完整性和连续确认；追加对照结果为 15.041s / 0.635s，与上述结果一致。

**结论：** 在该场景下，有积压分区暂停后，对其他空分区的长 fetch 会拖延恢复拉取。
缩短 fetch 等待消除了秒级空档。这与 ES 写入效率是两个独立问题，不能把 Session 耗时差
当作端到端吞吐提升比例。更短等待会增加空闲 fetch 请求量，仍需关注大量来源下的 broker 开销。

## 6. 结论边界与后续验证

本轮已分别验证归档/裁剪改进、大批次写入效果，以及 Kafka 尾部等待机制。尚未完成的验证包括：

- 最终自动合批配置与 100ms fetch 同时启用后的等长、独立数据状态对照及更长时间持续负载。
- 不同 Lifecycle 并发、ES CPU/内存规格和实际业务事件比例下的容量曲线。
- 大批次的低流量延迟、故障恢复时间，以及缩短 fetch 等待后的空闲请求开销。

因此，早期 440/s 的有限窗口结果与后期 937.3/s 的短时追赶结果都不应直接转换成生产 SLA。
当前证据支持优先改善请求粒度、同步依赖和拉取调度，不支持仅凭 ES 写队列为空、累计写盘量或
单次内存快照认定全部瓶颈所在。
